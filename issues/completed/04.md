# HU-04 — Observabilidad de errores internos y respuestas JSON consistentes

## Historia de usuario

**Como** desarrollador que opera la API de Bread King
**Quiero** que todo error interno (`500`) quede registrado en los logs con una marca visual
que lo distinga de los logs normales
**Para** diagnosticar incidentes sin exponer detalles técnicos al usuario final.

Además, **como** cliente de la API
**Quiero** que cualquier error —incluidos los inesperados— llegue siempre como `application/json`
con un mensaje genérico
**Para** poder procesar la respuesta de forma programática y sin filtrar información sensible.

## Alcance

Esta historia cubre **únicamente** la capa transversal de logging y manejo de errores de la API:

- Un **logger con niveles y resaltado visual** (highlights) que permita diferenciar de un
  vistazo un log normal, un `warn` y un `error`.
- El **middleware de manejo de errores** de Express que captura todo error no controlado,
  lo registra en los logs y responde `500`.
- La garantía de que **toda** respuesta de error sea `application/json` (nunca HTML),
  incluidos `404`, errores de parseo de JSON y errores internos.
- El **mensaje genérico** hacia el cliente (`{ "message": "Internal server error" }`) sin
  revelar la causa real, la cual solo se escribe en los logs.

No incluye logging estructurado a un servicio externo (ELK, Datadog, etc.), métricas,
tracing distribuido ni alertas (ver _Fuera de alcance_).

## Requerimientos funcionales

### RF-01 — Logger central con niveles y resaltado

- Debe existir un **módulo único de logging** (`src/config/logger.js` o
  `src/logger/index.js`) que exponga al menos los métodos `info`, `warn` y `error`.
- Cada nivel se imprime con una **etiqueta y color distintivos** para que sea identificable
  a simple vista en la terminal:

  | Nivel   | Etiqueta   | Color sugerido | Uso                                                        |
  | ------- | ---------- | -------------- | ---------------------------------------------------------- |
  | `info`  | `INFO`     | verde          | Arranque del servidor, peticiones y eventos normales.      |
  | `warn`  | `WARN`     | amarillo       | Situaciones esperadas pero anómalas (p. ej. `401`, `429`). |
  | `error` | `ERROR`    | rojo           | Errores internos (`500`) y fallos de infraestructura.      |

- El resaltado se logra con **códigos ANSI** aplicados por el propio logger, sin depender de
  librerías externas.
- Los colores deben desactivarse automáticamente cuando la salida no es una terminal
  interactiva (`process.stdout.isTTY` es falso) o cuando `NO_COLOR` está definido en el
  entorno, para que los logs en CI/Docker queden en texto plano legible.
- Cada línea de log incluye como mínimo: **timestamp ISO**, **nivel**, **mensaje** y, cuando
  aplique, un **contexto** (p. ej. `method`, `path`, `status`, `requestId`).
- El logger **nunca** debe imprimir contraseñas, tokens, códigos de recuperación ni el hash
  de la contraseña; el contexto que se le pase debe estar libre de esos valores.

### RF-02 — Registro de todo error interno

- Todo error que llegue al middleware de errores (es decir, cualquier `500`) debe registrarse
  con `logger.error(...)`.
- El log del error incluye:
  - El **mensaje** del error.
  - El **stack trace** completo (`error.stack`).
  - El **método y la ruta** de la petición (`req.method`, `req.originalUrl`).
  - El **estado HTTP** devuelto.
  - Un **identificador de la petición** (ver RF-05) para poder correlacionar el log con la
    respuesta entregada al cliente.
- Los errores controlados que ya tienen su propio código (`400`, `401`, `403`, `409`, `422`,
    `429`, `502`) **no** se registran como `error`; como máximo se registran como `warn`
    cuando aporten valor de diagnóstico (p. ej. `502` de envío de correo).
- El endpoint `GET /health` sigue respondiendo `503` cuando la base de datos no responde,
  pero ahora **también** registra el fallo con `logger.error(...)` incluyendo el error real.

### RF-03 — Respuestas de error siempre en JSON

- **Toda** respuesta de error de la API debe tener `Content-Type: application/json`; ninguna
  respuesta de error puede ser HTML (el comportamiento por defecto de Express 5 cuando un
  error no es manejado).
- Casos que deben cubrirse explícitamente:
  - Error interno no controlado → `500` con `{ "message": "Internal server error" }`.
  - Ruta inexistente → `404` con `{ "message": "Not found" }` (middleware de *not found*
    antes del manejador de errores).
  - Cuerpo con JSON malformado → `400` con `{ "message": "Invalid JSON body" }`, detectado
    desde el error de `express.json()` (`error.type === "entity.parse.failed"`).
  - Petición a `/docs` y a los endpoints existentes: sin cambios en sus respuestas exitosas.
- El manejador de errores debe usar `res.status(...).json(...)`, nunca `res.send(...)` con
  HTML ni `res.render(...)`.
- Si la respuesta ya fue enviada (`res.headersSent === true`), el middleware delega en
  `next(error)` para no romper el stream.

### RF-04 — Mensaje genérico hacia el usuario

- La respuesta `500` hacia el cliente es **siempre** la misma y **no** contiene:
  - El mensaje original del error.
  - El stack trace.
  - Nombres de tablas, columnas o consultas SQL.
  - Nombres de variables de entorno ni rutas del sistema de archivos.
- Contrato exacto:

  ```json
  { "message": "Internal server error" }
  ```

- El detalle técnico vive **únicamente** en los logs (RF-02).
- En producción (`NODE_ENV=production`) el mensaje genérico es obligatorio. En desarrollo se
  puede añadir un campo opcional `debug` con el mensaje del error **solo** si
  `NODE_ENV !== "production"`, para acelerar el diagnóstico local.

### RF-05 — Identificador de petición para correlación

- Cada petición recibe un `requestId` único (por ejemplo con `crypto.randomUUID()`), asignado
  por un middleware al inicio de la cadena.
- El `requestId` se incluye en todos los logs de esa petición y en la respuesta de error
  (`500`) como cabecera `X-Request-Id`, para poder cruzar la respuesta del cliente con la
  línea de log correspondiente.
- Si el cliente ya envía `X-Request-Id`, se respeta ese valor en lugar de generar uno nuevo.

### RF-06 — Registro de peticiones (log de acceso)

- Un middleware registra cada petición al finalizar la respuesta con `logger.info(...)`
  (o `logger.warn(...)` cuando el estado es `4xx`), incluyendo `method`, `path`, `status` y
  `requestId`.
- El log de acceso **no** debe incluir el cuerpo de la petición ni cabeceras sensibles
  (`Authorization`, `Cookie`).

## Requerimientos no funcionales

- **RNF-01** — Cada endpoint afectado debe mantener su bloque `@openapi` en el router del
  módulo; se agrega el esquema de la respuesta `500` genérica
  (`{ "message": "Internal server error" }`) y la respuesta `404` a la documentación de
  `/docs`.
- **RNF-02** — Desarrollo guiado por pruebas (TDD): primero el test Jest que falla
  (`src/config/logger.test.js` y `src/app.test.js`), luego la implementación.
- **RNF-03** — Cobertura de pruebas > 90%. Los tests deben poder **silenciar** el logger
  (inyección o `jest.spyOn`) para no ensuciar la salida de `npm test`.
- **RNF-04** — Ningún archivo debe superar las 300 líneas; dividir en módulos si es necesario
  (logger, middleware de request-id, middleware de errores y registro de peticiones por
  separado).
- **RNF-05** — Formatear cada archivo modificado con Prettier antes de finalizar.
- **RNF-06** — El acceso a datos se hace con Sequelize 6 sobre Postgres; nunca con consultas
  crudas de `pg`.
- **RNF-07** — Seguridad: los logs no contienen secretos (RF-01) y el cliente nunca recibe el
  detalle del error (RF-04).
- **RNF-08** — El logger no debe depender de librerías externas nuevas; usa `console` y
  códigos ANSI del estándar.
- **RNF-09** — El middleware de errores debe ser el **último** registrado en `src/app.js`, y
  el de *not found* debe ir inmediatamente antes, para que ninguna ruta quede sin cubrir.

## Contrato de la API

### Respuesta `500` (error interno no controlado)

```json
{ "message": "Internal server error" }
```

Cabecera adicional:

```
X-Request-Id: <uuid>
```

### Respuesta `404` (ruta inexistente)

```json
{ "message": "Not found" }
```

### Respuesta `400` (JSON malformado en el cuerpo)

```json
{ "message": "Invalid JSON body" }
```

### Ejemplo de log de error

```
2026-09-13T10:15:32.104Z ERROR 500 POST /users :: connection refused
    at User.findAll (/app/src/users/index.js:120:15)
    at Layer.handle (/app/node_modules/express/lib/router/layer.js:95:5)
    requestId=3f1c9b6e-... method=POST path=/users
```

### Ejemplo de log normal

```
2026-09-13T10:15:31.002Z INFO 200 GET /health requestId=8a2d...
```

## Criterios de aceptación

- [ ] Existe un logger con niveles `info`, `warn` y `error` que resalta cada nivel con un
      color distinto en la terminal.
- [ ] Los colores se desactivan cuando la salida no es una TTY o cuando `NO_COLOR` está
      definido.
- [ ] Cualquier error interno (`500`) queda registrado en los logs con stack trace, método,
      ruta y `requestId`.
- [ ] La respuesta al cliente para un error interno es siempre
      `{ "message": "Internal server error" }` y **no** revela la causa.
- [ ] Ninguna respuesta de error de la API es HTML: todas son `application/json`.
- [ ] Una ruta inexistente responde `404` con `{ "message": "Not found" }` en JSON.
- [ ] Un cuerpo con JSON malformado responde `400` con `{ "message": "Invalid JSON body" }`
      en JSON.
- [ ] `GET /health` con la base de datos caída responde `503` en JSON y además registra el
      error en los logs.
- [ ] Cada respuesta de error `500` incluye la cabecera `X-Request-Id` y ese mismo id aparece
      en la línea de log del error.
- [ ] Los logs no contienen contraseñas, tokens ni códigos de recuperación.
- [ ] Los endpoints existentes (`/hello-world`, `/health`, `/auth/*`, `/users`) mantienen sus
      respuestas exitosas sin cambios.
- [ ] Los endpoints y las nuevas respuestas `500`/`404` aparecen documentados en `/docs`.
- [ ] `npm test` pasa con cobertura > 90%.

## Fuera de alcance

- Envío de logs a servicios externos (ELK, Datadog, Sentry, CloudWatch).
- Métricas, tracing distribuido y alertas.
- Rotación de archivos de log o escritura en disco (la salida es stdout/stderr).
- Reintentos automáticos o *circuit breakers* ante fallos de la base de datos.
- Cambios en los códigos de error ya definidos por HU-01/HU-02/HU-03 (`400`, `401`, `403`,
  `409`, `422`, `429`, `502`), salvo el registro opcional como `warn`.
- Internacionalización de los mensajes de error.

## Dependencias técnicas

- Sin nuevas dependencias externas: se usa `console`, `crypto` y códigos ANSI.
- Nuevas variables de entorno (documentarlas en `.env.example`):

  | Variable   | Uso                                                                  |
  | ---------- | -------------------------------------------------------------------- |
  | `NODE_ENV` | `production` activa el mensaje genérico estricto (sin `debug`).      |
  | `LOG_LEVEL`| Nivel mínimo a imprimir (`info` por defecto; `warn` o `error` para reducir ruido). |
  | `NO_COLOR` | Si está definida, desactiva el resaltado ANSI (estándar de facto).   |

- Nuevos archivos previstos:
  - `src/config/logger.js` — logger con niveles, resaltado ANSI y contexto.
  - `src/config/logger.test.js` — pruebas Jest del logger.
  - `src/middleware/request-id.js` — asigna/propaga `requestId`.
  - `src/middleware/error-handler.js` — middleware de errores (500 genérico + log).
  - `src/middleware/not-found.js` — middleware 404 en JSON.
  - `src/middleware/request-logger.js` — log de acceso por petición.
  - `src/middleware/*.test.js` — pruebas Jest de cada middleware.
- Archivos a modificar:

    (este último al final), y manejar el error de `express.json()`.
  - `src/index.js` — reemplazar el `console.log` de arranque por `logger.info(...)`.
  - `src/health/index.js` — registrar con `logger.error(...)` el fallo de la base de datos.
  - `src/config/swagger.js` — agregar el esquema de la respuesta `500` genérica.
  - `src/app.test.js` — cubrir `404`, JSON malformado, `500` genérico y `Content-Type`.
  - `README.md` — documentar el formato de los logs, el mensaje genérico de error y las
    nuevas variables de entorno.
  - `.env.example` — agregar `NODE_ENV`, `LOG_LEVEL` y `NO_COLOR`.
