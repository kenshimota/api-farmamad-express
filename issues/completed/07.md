# HU-07 — Catálogo de roles: listado de roles disponibles

## Historia de usuario

**Como** administrador de Bread King
**Quiero** consultar el catálogo de roles que existen en el sistema
**Para** saber qué roles puedo asignar al crear un usuario, sin tener que leer el
seeder ni la documentación del repositorio.

Además, **como** frontend del panel de administración
**Quiero** obtener los roles desde la API
**Para** poblar el selector de rol de `POST /users` con datos reales y dejar de
tener la lista de roles escrita a mano en el cliente.

## Alcance

Esta historia cubre **únicamente** la lectura del catálogo de roles:

- El **listado de roles** (`GET /roles`), protegido y exclusivo del administrador.
- La lectura del catálogo desde la tabla `roles` con Sequelize (nunca con
  consultas crudas de `pg`).

No incluye crear, editar ni eliminar roles, ni permisos granulares por rol (ver
_Fuera de alcance_).

## Requerimientos funcionales

### RF-01 — Listado de roles (`GET /roles`)

- Endpoint **protegido**: requiere `Authorization: Bearer <token>` con rol `admin`.
- Devuelve la colección de roles registrados con los datos públicos de cada uno
  (`id`, `name`), **sin** `createdAt` ni `updatedAt`.
- Responde `200` con un arreglo JSON:

  ```json
  [
    { "id": 1, "name": "admin" },
    { "id": 2, "name": "seller" },
    { "id": 3, "name": "delivery" },
    { "id": 4, "name": "freelance_delivery" },
    { "id": 5, "name": "customer" }
  ]
  ```

- El orden es estable y predecible: por `id` ascendente.
- Si la tabla `roles` está vacía, responde `200` con `[]` (nunca `404`).
- Un usuario autenticado sin rol `admin` recibe `403` con `{ "message": "Forbidden" }`.
- Sin token, token inválido o expirado responde `401` con `{ "message": "Unauthorized" }`.
- Un usuario bloqueado recibe `403` con `{ "message": "User is blocked" }` (HU-05).

### RF-02 — Serialización del rol

- Cada elemento del arreglo expone **solo** `id` y `name`.
- Las columnas de auditoría (`createdAt`, `updatedAt`) no se exponen: el listado
  se construye con un serializador explícito y no con `toJSON()` del modelo.
- El nombre del rol coincide exactamente con el valor aceptado por `POST /users`
  (HU-02), de modo que el cliente puede usar la respuesta como fuente de verdad
  para el campo `role`.

### RF-03 — Autorización: solo el administrador

- `GET /roles` usa los middlewares existentes `authenticate` (HU-01) y
  `authorize("admin")` (HU-02), apoyados en `req.user.role`.
- Ningún otro rol (`seller`, `delivery`, `freelance_delivery`, `customer`) puede
  listar roles: todos reciben `403` con `{ "message": "Forbidden" }`.
- El endpoint no acepta parámetros, cuerpo ni filtros: cualquier `query` enviada
  por el cliente se ignora y la respuesta es siempre el catálogo completo.

## Requerimientos no funcionales

- **RNF-02** — Desarrollo guiado por pruebas (TDD): primero los tests Jest que

- **RNF-03** — Cobertura de pruebas > 90%, con pruebas unitarias (modelo mockeado)
  y de integración contra Postgres real (`src/roles/roles.integration.test.js`).
- **RNF-04** — Ningún archivo debe superar las 300 líneas.
- **RNF-05** — Formatear cada archivo modificado con Prettier antes de finalizar.
- **RNF-06** — El acceso a datos se hace con Sequelize 6 sobre Postgres; nunca con

- **RNF-07** — El endpoint es de solo lectura: no modifica la tabla `roles` ni

- **RNF-08** — El listado no expone columnas de auditoría ni información sensible;
  el catálogo no contiene datos personales.
- **RNF-09** — Se reutiliza el módulo `src/auth/roles.js` como punto de entrada al

## Contrato de la API

### `GET /roles`

Header: `Authorization: Bearer <jwt>` (rol `admin`).

```bash
curl http://localhost:3001/roles -H "Authorization: Bearer <jwt>"
```

Respuesta `200`:

```json
[
  { "id": 1, "name": "admin" },
  { "id": 2, "name": "seller" },
  { "id": 3, "name": "delivery" },
  { "id": 4, "name": "freelance_delivery" },
  { "id": 5, "name": "customer" }
]
```

Respuesta `401` (token ausente, inválido o expirado):

```json
{ "message": "Unauthorized" }
```

Respuesta `403` (usuario autenticado sin rol `admin` o usuario bloqueado):

```json
{ "message": "Forbidden" }
```

## Criterios de aceptación

- [ ] `GET /roles` devuelve el catálogo con `id` y `name`, ordenado por `id` ascendente.
- [ ] La respuesta no incluye `createdAt` ni `updatedAt`.
- [ ] `GET /roles` responde `[]` cuando la tabla `roles` está vacía.
- [ ] `GET /roles` sin token responde `401` con `{ "message": "Unauthorized" }`.
- [ ] `GET /roles` con un token inválido o expirado responde `401`.
- [ ] Los roles `seller`, `delivery`, `freelance_delivery` y `customer` reciben `403`.
- [ ] Un administrador bloqueado recibe `403` con `{ "message": "User is blocked" }`.
- [ ] El endpoint aparece documentado en `/docs` y en `README.md`.
- [ ] `npm test` pasa con cobertura > 90%.

## Fuera de alcance

- Crear, editar o eliminar roles (`POST/PUT/PATCH/DELETE /roles`).
- Permisos granulares por rol o matriz de permisos.
- Paginación, filtros y búsqueda en `GET /roles`.
- Asignación masiva de roles o cambio de rol de un usuario existente.
- Roles por organización o multi-tenant.
