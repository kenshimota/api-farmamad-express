# HU-03 — Recuperación de contraseña con código OTP enviado por email

## Historia de usuario

**Como** usuario registrado en Bread King que olvidó su contraseña
**Quiero** solicitar un código de recuperación a mi email y usarlo para definir una nueva contraseña
**Para** volver a acceder a la aplicación sin depender de un administrador.

Además, **como** usuario que acaba de validar su código
**Quiero** recibir un JWT válido
**Para** quedar con la sesión iniciada inmediatamente después de cambiar mi contraseña.

## Alcance

Esta historia cubre **únicamente** el flujo de recuperación de contraseña:

- Solicitud del código OTP por email (`POST /auth/forgot-password`).
- Validación del código OTP y emisión de un JWT (`POST /auth/verify-reset-code`).
- Cambio de contraseña con el JWT emitido (`POST /auth/reset-password`).

No incluye registro de usuarios, login, roles/permisos ni cambio de contraseña de un
usuario autenticado que conoce su contraseña actual (ver _Fuera de alcance_).

## Requerimientos funcionales

### RF-01 — Modelo del código de recuperación

- Todo código se guarda en una **tabla `password_reset_codes`** (modelo Sequelize
  `PasswordResetCode`), **no** en memoria ni en la tabla `users`.
- Campos mínimos:

  | Campo        | Tipo          | Reglas                                                                 |
  | ------------ | ------------- | ---------------------------------------------------------------------- |
  | `id`         | INTEGER       | PK autoincremental.                                                    |
  | `userId`     | INTEGER       | FK hacia `users.id`, `allowNull: false`, `onDelete: CASCADE`.          |
  | `codeHash`   | STRING        | Hash bcrypt del código de 8 dígitos; `allowNull: false`.               |
  | `expiresAt`  | DATE          | `allowNull: false`; momento en que el código deja de ser válido.       |
  | `consumedAt` | DATE          | `allowNull: true`; se llena cuando el código se usa o se invalida.     |
  | `createdAt`  | DATE          | Timestamp de creación.                                                 |
  | `updatedAt`  | DATE          | Timestamp de actualización.                                            |

- El código **nunca** se almacena en texto plano: se guarda como hash bcrypt
  (mismo `hashPassword` de `src/auth/password.js`).
- Asociación Sequelize: `PasswordResetCode.belongsTo(User)` y
  `User.hasMany(PasswordResetCode)`, con `foreignKey: "userId"`.

### RF-02 — Solicitud del código (`POST /auth/forgot-password`)

- Endpoint **público** (no requiere autenticación).
- Campo requerido en el cuerpo: `email`.
- Si el email no corresponde a ningún usuario, la respuesta es **idéntica** a la del
  caso exitoso (`200` con mensaje genérico), para no revelar qué emails están
  registrados (enumeración de usuarios). En ese caso no se envía ningún correo.
- Si el email existe:
  - Se genera un código aleatorio de **8 dígitos numéricos** (con ceros a la
    izquierda permitidos, p. ej. `00427193`).
  - Se envía por email con **Nodemailer** (ver RF-06).
  - Se persiste el hash del código con `expiresAt = now + 5 minutos`.
  - Responde `200` con `{ "message": "If the email exists, a recovery code was sent" }`.
- **Unicidad del código válido (RF-04):** antes de crear el nuevo código se invalidan
  (se marcan como consumidos) todos los códigos anteriores del usuario que sigan
  vigentes. Nunca pueden coexistir dos códigos válidos.
- **Cooldown de reenvío (RF-05):** solo se puede emitir un código nuevo si han pasado
  **al menos 2 minutos** desde el último código emitido para ese usuario. Si no, responde
  `429` con `{ "message": "Please wait before requesting a new code" }` y no se envía correo.
- Si faltan campos obligatorios, responde `400`.
- Si el email tiene formato inválido, responde `422` con la estructura de errores.

### RF-03 — Validación del código y emisión del JWT (`POST /auth/verify-reset-code`)

- Endpoint **público** (no requiere autenticación).
- Campos requeridos: `email` y `code`.
- `code` debe ser una cadena de exactamente 8 dígitos numéricos.
- El sistema busca el **último código no consumido** del usuario y comprueba:
  1. Que exista un código vigente para ese usuario.
  2. Que `expiresAt` no haya pasado (máximo **5 minutos** desde su emisión).
  3. Que el código enviado coincida con el `codeHash` (bcrypt).
- Si el código es válido:
  - Se marca como consumido (`consumedAt = now`), de modo que no pueda reutilizarse.
  - Se responde `200` con un **JWT** firmado (mismo `signToken` de `src/auth/index.js`)
    y los datos públicos del usuario, para que la sesión quede iniciada:

    ```json
    {
      "token": "<jwt>",
      "user": { "id": 1, "username": "juan", "email": "juan@example.com", "name": "Juan", "role": "customer" }
    }
    ```

- Si el código es inválido, expirado o no existe, responde `401` con un mensaje
  **genérico** (`{ "message": "Invalid or expired code" }`), sin distinguir el motivo.
- Si faltan campos obligatorios, responde `400`.
- Si el formato de `email` o `code` es inválido, responde `422` con la estructura de errores.
- El JWT emitido aquí es el mismo tipo de token que emite `POST /auth/login` y sirve
  para llamar a `POST /auth/reset-password` y a cualquier endpoint protegido.

### RF-04 — Un único código válido a la vez

- Para un mismo usuario **no pueden coexistir dos códigos válidos**.
- Al emitir un código nuevo, todos los anteriores que sigan vigentes se marcan como
  consumidos dentro de la **misma transacción** que crea el nuevo código.
- La emisión y la validación del código se ejecutan dentro de una transacción
  (`sequelize.transaction`) para evitar condiciones de carrera (dos solicitudes
  simultáneas o dos validaciones del mismo código a la vez).
- Un código ya consumido no puede volver a usarse, aunque no haya expirado.

### RF-05 — Vigencia y cooldown

- **Vigencia:** un código es válido durante **5 minutos** desde su emisión
  (`expiresAt = createdAt + 5 minutos`). Pasado ese tiempo no se acepta.
- **Cooldown:** solo se puede solicitar un código nuevo si han pasado **al menos 2
  minutos** desde la emisión del último código de ese usuario. Si no ha pasado el
  tiempo, responde `429` (ver RF-02).
- Los tiempos se calculan con la fecha del servidor y se persisten en la base de datos
  (no en memoria), de modo que sobreviven a reinicios del proceso.
- Los valores `5 minutos` y `2 minutos` deben definirse como constantes con nombre
  (por ejemplo `CODE_TTL_MINUTES` y `RESEND_COOLDOWN_MINUTES`) para poder ajustarlos
  y testearlos sin duplicar literales.

### RF-06 — Envío del email con Nodemailer (Gmail)

- El envío se hace con **Nodemailer** (`nodemailer`), encapsulado en un módulo
  (`src/auth/mailer.js`) que expone una función del tipo
  `sendRecoveryCode(email, code)`.
- El servicio de correo es **Gmail**, configurado **únicamente** con dos variables de
  entorno:
  - `GMAIL_USERNAME`: la cuenta de Gmail desde la que se envía (también es el remitente).
  - `GMAIL_TOKEN`: el **App Password** de Gmail (contraseña de aplicación de 16
    caracteres), nunca la contraseña normal de la cuenta.
- El transporte se construye con el servicio `gmail` de Nodemailer:

  ```js
  nodemailer.createTransport({
    service: "gmail",
    auth: { user: process.env.GMAIL_USERNAME, pass: process.env.GMAIL_TOKEN },
  });
  ```

- No se usan variables `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_SECURE`
  ni `MAIL_FROM`: el remitente (`from`) es `GMAIL_USERNAME`.
- El asunto y el cuerpo del correo son en español e incluyen el código de 8 dígitos y
  su vigencia de 5 minutos.
- El transporte se crea de forma perezosa y se puede inyectar/reemplazar en las pruebas
  para no enviar correos reales durante `npm test`.
- Si el envío falla, el endpoint responde `502` con
  `{ "message": "Could not send the recovery email" }` y **no** deja un código válido
  persistido (la transacción se revierte).

### RF-07 — Cambio de contraseña (`POST /auth/reset-password`)

- Endpoint **protegido**: requiere `Authorization: Bearer <token>` con el JWT obtenido
  en `POST /auth/verify-reset-code` (o en `POST /auth/login`).
- Campos requeridos: `password` y `passwordConfirmation`.
- Reglas de la contraseña: mínimo **8 caracteres** (misma regla que HU-01/HU-02).
- `passwordConfirmation` debe coincidir con `password`; si no, responde `422` con
  `{ "errors": { "passwordConfirmation": "Passwords do not match" } }`.
- Si todo es correcto:
  - Se actualiza el hash de la contraseña del usuario autenticado (hook `beforeUpdate`
    del modelo `User`).
  - Se invalidan todos los códigos de recuperación pendientes de ese usuario
    (`consumedAt = now`), para que no quede ningún código utilizable.
  - Responde `200` con `{ "message": "Password updated" }`.
- Si el token falta, es inválido o está expirado, responde `401`.
- Si faltan campos obligatorios, responde `400`.
- Si la nueva contraseña no cumple las reglas, responde `422` con la estructura de errores.
- La contraseña nunca se devuelve en la respuesta ni se guarda en texto plano.

### RF-08 — Validación de campos

- Se valida con `yup` (mismo enfoque que HU-01 y HU-02), reutilizando
  `formatValidationErrors`, `missingFields` y `requiredFieldsMessage`.
- Faltan campos obligatorios → `400` con `{ "message": "<campos> are required" }`.
- Campos inválidos (email mal formado, código que no tiene 8 dígitos, contraseña corta)
  → `422` con la estructura de errores y los mensajes **en español**, igual que HU-02.
- Los esquemas viven en `src/auth/validators.js` (o en un archivo de validadores del
  submódulo) para no duplicar reglas.

## Requerimientos no funcionales

- **RNF-01** — Cada endpoint debe documentarse con un bloque `@openapi` en el router del
  módulo para que sea visible en `/docs` (Swagger UI), incluyendo el esquema del código
  de recuperación y las nuevas respuestas `429` y `502`.
- **RNF-02** — Desarrollo guiado por pruebas (TDD): primero el test Jest que falla
  (`src/auth/password-reset.test.js`), luego la implementación.
- **RNF-03** — Cobertura de pruebas > 90%; en las pruebas unitarias el mailer y el reloj
  deben poder sustituirse (mocks) para no depender de SMTP ni de esperas reales.
- **RNF-04** — Ningún archivo debe superar las 300 líneas; dividir en módulos si es
  necesario (router, validadores, mailer y servicio de códigos por separado).
- **RNF-05** — Formatear cada archivo modificado con Prettier antes de finalizar.
- **RNF-06** — El acceso a datos se hace con Sequelize 6 sobre Postgres; nunca con
  consultas crudas de `pg`.
- **RNF-07** — Seguridad: no se revela si un email está registrado (RF-02), el código se
  guarda hasheado (RF-01), un código solo se usa una vez (RF-03/RF-04) y no pueden
  coexistir dos códigos válidos (RF-04).
- **RNF-08** — Concurrencia: la emisión y el consumo del código se hacen en transacción
  para que dos peticiones simultáneas no creen ni acepten dos códigos válidos.
- **RNF-09** — El código de 8 dígitos se genera con una fuente criptográficamente segura
  (`crypto.randomInt`), no con `Math.random()`.

## Contrato de la API

### `POST /auth/forgot-password`

Sin autenticación.

Petición:

```json
{ "email": "juan@example.com" }
```

Respuesta `200` (exista o no el email):

```json
{ "message": "If the email exists, a recovery code was sent" }
```

Respuesta `400` (falta el email):

```json
{ "message": "email is required" }
```

Respuesta `422` (email inválido):

```json
{ "errors": { "email": "Email inválido" } }
```

Respuesta `429` (todavía no pasan 2 minutos desde el último código):

```json
{ "message": "Please wait before requesting a new code" }
```

Respuesta `502` (falló el envío del correo):

```json
{ "message": "Could not send the recovery email" }
```

### `POST /auth/verify-reset-code`

Sin autenticación.

Petición:

```json
{ "email": "juan@example.com", "code": "00427193" }
```

Respuesta `200` (código válido; inicia sesión):

```json
{
  "token": "<jwt>",
  "user": {
    "id": 1,
    "username": "juan",
    "email": "juan@example.com",
    "name": "Juan",
    "role": "customer"
  }
}
```

Respuesta `400` (faltan campos):

```json
{ "message": "email and code are required" }
```

Respuesta `401` (código inválido, expirado o ya usado):

```json
{ "message": "Invalid or expired code" }
```

Respuesta `422` (formato inválido):

```json
{ "errors": { "code": "El código debe tener 8 dígitos" } }
```

### `POST /auth/reset-password`

Header: `Authorization: Bearer <jwt>`.

Petición:

```json
{ "password": "nuevaClave123", "passwordConfirmation": "nuevaClave123" }
```

Respuesta `200`:

```json
{ "message": "Password updated" }
```

Respuesta `400` (faltan campos):

```json
{ "message": "password and passwordConfirmation are required" }
```

Respuesta `401` (token ausente, inválido o expirado):

```json
{ "message": "Unauthorized" }
```

Respuesta `422` (contraseña corta o confirmación distinta):

```json
{ "errors": { "passwordConfirmation": "Passwords do not match" } }
```

## Criterios de aceptación

- [ ] Puedo solicitar un código con `POST /auth/forgot-password` enviando mi email.
- [ ] Recibo en mi correo un código de 8 dígitos numéricos enviado con Nodemailer.
- [ ] Si el email no existe, la respuesta es `200` con el mismo mensaje genérico y no se envía correo.
- [ ] El código es válido durante 5 minutos; después de ese tiempo `POST /auth/verify-reset-code` responde `401`.
- [ ] Si pido un código nuevo antes de 2 minutos desde el último, recibo `429` y no se envía correo.
- [ ] Si pido un código nuevo después de 2 minutos, el anterior deja de ser válido y solo el nuevo se acepta.
- [ ] Un código ya usado no puede volver a usarse.
- [ ] Validar el código con `POST /auth/verify-reset-code` responde `200` con un JWT y los datos del usuario.
- [ ] Con ese JWT puedo llamar a `POST /auth/reset-password` y cambiar mi contraseña.
- [ ] Tras el cambio, puedo iniciar sesión con `POST /auth/login` usando la nueva contraseña.
- [ ] `POST /auth/reset-password` sin token responde `401`; con contraseñas que no coinciden responde `422`.
- [ ] Tras cambiar la contraseña no queda ningún código de recuperación válido para el usuario.
- [ ] El código nunca se guarda en texto plano y nunca aparece en las respuestas.
- [ ] Los tres endpoints aparecen documentados en `/docs`.
- [ ] `npm test` pasa con cobertura > 90%.

## Fuera de alcance

- Registro de usuarios y login (HU-01/HU-02).
- Cambio de contraseña de un usuario autenticado que conoce su contraseña actual
  (requeriría pedir la contraseña vigente).
- Recuperación por SMS, preguntas de seguridad o enlaces mágicos.
- Refresh tokens y cierre de sesión.
- Invalidación global de sesiones activas al cambiar la contraseña.
- Cola/worker de correos: el envío es síncrono dentro de la petición.
