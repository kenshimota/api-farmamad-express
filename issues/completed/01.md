# HU-01 — Inicio de sesión de usuario (autenticación con JWT)

## Historia de usuario

**Como** usuario registrado en Farmamad
**Quiero** iniciar sesión con mi email o mi nombre de usuario y mi contraseña
**Para** obtener un token (JWT) que me permita acceder a la aplicación para poder consultar, crear y editar mi propia información.

## Alcance

Esta historia cubre **únicamente** el inicio de sesión y el endpoint para consultar
la información del usuario autenticado. No incluye registro de usuarios, recuperación
de contraseña, roles/permisos ni refresh tokens (ver _Fuera de alcance_).

## Requerimientos funcionales

### RF-01 — Modelo de usuario

- Todo usuario debe tener los campos obligatorios: `username`, `email` y `password`.
- `username` y `email` deben ser únicos (no se permiten duplicados).
- `password` **nunca** se almacena en texto plano: se guarda como hash (bcrypt).
- El usuario puede tener además campos opcionales como `name` y `createdAt`.

### RF-02 — Inicio de sesión

- Endpoint: `POST /auth/login`.
- El cuerpo de la petición acepta **un identificador** (`identifier`) y una `password`:
  - `identifier` puede ser el **email** o el **username** del usuario.
  - `password` es obligatoria.
- El sistema busca al usuario por `email` **o** por `username` (lo que coincida con `identifier`).
- Si las credenciales son correctas, responde `200` con un JWT.
- Si el usuario no existe **o** la contraseña es incorrecta, responde `401` con un
  mensaje genérico (`Invalid credentials`), sin revelar cuál de los dos falló.
- Si faltan campos obligatorios, responde `400`.
- Si algun campo es inválido, responde `422` con un mensaje genérico. con una estructura de errores. recomiendo usar `yup` para validar los campos.

### RF-03 — Generación del JWT

- El token se firma con `HS256` usando el secreto `JWT_SECRET` (variable de entorno).
- El payload incluye como mínimo:
  - `sub`: id del usuario.
  - `username`: nombre de usuario.
  - `email`: email del usuario.
  - `iat` y `exp`: emisión y expiración.
- La expiración es configurable vía `JWT_EXPIRES_IN` (por defecto `1h`).
- La respuesta del login incluye el token y datos básicos del usuario (sin `password`).

### RF-04 — Acceso protegido a la información propia

- Endpoint: `GET /auth/me`.
- Requiere el header `Authorization: Bearer <token>`.
- Si el token es válido, responde `200` con la información del usuario autenticado
  (`id`, `username`, `email`, `name`), sin exponer el hash de la contraseña.
- Si el token falta, es inválido o está expirado, responde `401`.
- Por ahora este es el **único** recurso al que el usuario autenticado tiene acceso.

## Requerimientos no funcionales

- **RNF-01** — Cada endpoint debe documentarse con un bloque `@openapi` en el router
  del módulo para que sea visible en `/docs` (Swagger UI).
- **RNF-02** — Desarrollo guiado por pruebas (TDD): primero el test Jest que falla
  (`src/auth/auth.test.js`), luego la implementación (`src/auth/index.js`).
- **RNF-03** — Cobertura de pruebas > 90%.
- **RNF-04** — Ningún archivo debe superar las 300 líneas; dividir en módulos si es necesario.
- **RNF-05** — Formatear cada archivo modificado con Prettier antes de finalizar.
- **RNF-06** — El acceso a datos se hace con Sequelize 6 sobre Postgres; nunca con
  consultas crudas de `pg`.

## Contrato de la API

### `POST /auth/login`

Petición:

```json
{
  "identifier": "juan@example.com",
  "password": "secreto123"
}
```

Respuesta `200`:

```json
{
  "token": "<jwt>",
  "user": {
    "id": 1,
    "username": "juan",
    "email": "juan@example.com",
    "name": "Juan"
  }
}
```

Respuesta `400` (campos faltantes):

```json
{ "message": "identifier and password are required" }
```

Respuesta `401` (credenciales inválidas):

```json
{ "message": "Invalid credentials" }
```

Respuesta `422` (campos inválidos):

```json
{
  "errors": {
    "email": "Invalid email",
    "password": "Password must be at least 8 characters long"
  }
}
```

### `GET /auth/me`

Header: `Authorization: Bearer <jwt>`

Respuesta `200`:

```json
{
  "id": 1,
  "username": "juan",
  "email": "juan@example.com",
  "name": "Juan"
}
```

Respuesta `401` (token ausente, inválido o expirado):

```json
{ "message": "Unauthorized" }
```

## Criterios de aceptación

- [ ] Puedo iniciar sesión usando mi **email** y mi contraseña.
- [ ] Puedo iniciar sesión usando mi **username** y mi contraseña.
- [ ] Con credenciales válidas recibo un JWT firmado y con expiración.
- [ ] Con credenciales inválidas recibo `401` con mensaje genérico.
- [ ] Con campos faltantes recibo `400`.
- [ ] Con el JWT puedo consultar `GET /auth/me` y ver mi información.
- [ ] `GET /auth/me` sin token o con token inválido/expirado responde `401`.
- [ ] La contraseña nunca aparece en ninguna respuesta ni se guarda en texto plano.
- [ ] Ambos endpoints aparecen documentados en `/docs`.
- [ ] `npm test` pasa con cobertura > 90%.

## Fuera de alcance

- Registro de nuevos usuarios (`POST /auth/register`).
- Recuperación / cambio de contraseña.
- Refresh tokens y cierre de sesión (revocación de tokens).
- Roles y permisos; cualquier recurso distinto a `GET /auth/me`.

## Dependencias técnicas

- Nuevas dependencias: `jsonwebtoken` (firma/verificación de JWT) y `bcrypt`
  (hash de contraseñas).
- Nuevas variables de entorno: `JWT_SECRET` (obligatoria) y `JWT_EXPIRES_IN`
  (opcional, por defecto `1h`). Documentarlas en `.env.example`.
- Nuevos archivos previstos:
  - `src/auth/index.js` — router con `POST /auth/login` y `GET /auth/me`.
  - `src/auth/auth.test.js` — pruebas Jest.
  - `src/auth/middleware.js` — middleware de verificación del JWT.
  - `src/models/user.js` — modelo Sequelize `User`.
