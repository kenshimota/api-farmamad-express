# HU-08 — Gestión de clientes: registro, consulta, edición y eliminación

## Historia de usuario

**Como** administrador o vendedor de Bread King
**Quiero** registrar clientes con su nombre completo, ubicación y email
**Para** tener un directorio de clientes al que asignar pedidos y entregas.

Además, **como** administrador, vendedor o repartidor
**Quiero** consultar los clientes registrados
**Para** conocer a quién hay que entregarle un pedido y a dónde debe ir.

Además, **como** administrador o vendedor
**Quiero** corregir los datos de un cliente o eliminarlo cuando ya no corresponde
**Para** mantener el directorio actualizado y sin registros obsoletos.

## Alcance

Esta historia cubre **únicamente** el CRUD del directorio de clientes:

- El **registro de clientes** (`POST /customers`), permitido a `admin` y `seller`.
- La **consulta de clientes** (`GET /customers` y `GET /customers/:id`), permitida a
  `admin`, `seller` y `delivery`.
- La **edición de clientes** (`PUT /customers/:id`), permitida a `admin` y `seller`.
- La **eliminación de clientes** (`DELETE /customers/:id`), permitida a `admin` y `seller`.

No incluye pedidos, asignación de clientes a repartidores, geocodificación de direcciones
ni el historial de compras del cliente (ver _Fuera de alcance_).

## Requerimientos funcionales

### RF-01 — Modelo del cliente

- Todo cliente se guarda en una **tabla `customers`** (modelo Sequelize `Customer`), **no**
  en la tabla `users`: un cliente es un tercero al que se le vende, no un usuario que inicia
  sesión.
- Campos mínimos:

  | Campo          | Tipo          | Reglas                                                                     |
  | -------------- | ------------- | -------------------------------------------------------------------------- |
  | `id`           | INTEGER       | PK autoincremental.                                                        |
  | `fullName`     | STRING        | `allowNull: false`; nombre completo del cliente.                           |
  | `latitude`     | DECIMAL(10,7) | `allowNull: true`; latitud de la dirección (rango `-90` a `90`).           |
  | `longitude`    | DECIMAL(10,7) | `allowNull: true`; longitud de la dirección (rango `-180` a `180`).        |
  | `direction`    | STRING        | `allowNull: false`; dirección textual donde se entrega el pedido.          |
  | `email`        | STRING        | `allowNull: false`, `unique: true`; validado con `isEmail`.                |
  | `isRegistered` | BOOLEAN       | `allowNull: false`; indica si el cliente ha sido registrado. como usuario. |
  | `createdAt`    | DATE          | Timestamp de creación.                                                     |
  | `updatedAt`    | DATE          | Timestamp de actualización.                                                |

- `latitude` y `longitude` se persisten como `DECIMAL`, no como `FLOAT`, para no perder
  precisión al devolverlas; la API las expone como **número** en JSON.
- El modelo expone un `toJSON` que devuelve exactamente `id`, `fullName`, `latitude`,
  `longitude`, `direction` y `email` (sin columnas de auditoría ni campos internos).
- El email es único: si ya existe otro cliente con ese email, la creación responde `409`
  (RF-03).
- No hay borrado lógico: la eliminación es física (RF-06).
- Hay que verificar que el cliente está registrado como usuario (RF-07), validando si ese email ya es un usuario.

### RF-02 — Registro de clientes (`POST /customers`)

- Endpoint **protegido**: requiere `Authorization: Bearer <token>` con rol `admin` o
  `seller`.
- Campos requeridos: `fullName`, `latitude`, `longitude`, `direction`, `isRegistered` y `email`.
- Si la creación es exitosa responde `201` con los datos públicos del cliente.
- Si `email` ya está registrado, responde `409` con
  `{ "message": "Customer already exists" }`.
- Un usuario autenticado con rol `delivery`, `freelance_delivery` o `customer` recibe `403`
  con `{ "message": "Forbidden" }`.
- Sin token, token inválido o expirado responde `401` con `{ "message": "Unauthorized" }`.
- Un usuario bloqueado recibe `403` con `{ "message": "User is blocked" }` (HU-05).

### RF-03 — Consulta de clientes (`GET /customers` y `GET /customers/:id`)

- Endpoints **protegidos**: requieren `Authorization: Bearer <token>` con rol `admin`,
  `seller` o `delivery`.
- `GET /customers` devuelve la colección completa, ordenada por `id` ascendente:

  ```json
  [
    {
      "id": 1,
      "fullName": "Juan Pérez",
      "latitude": -17.7833,
      "longitude": -63.1821,
      "direction": "Av. Monseñor Rivero 123",
      "email": "juan@example.com"
    }
  ]
  ```

- Si no hay clientes, responde `200` con `[]` (nunca `404`).
- `GET /customers/:id` devuelve un único cliente.
- Si el `id` no corresponde a ningún cliente, responde `404` con
  `{ "message": "Customer not found" }`.
- Si `:id` no es un entero positivo, responde `422` con
  `{ "errors": { "id": "Invalid customer id" } }`.
- El rol `delivery` **solo** puede leer: no puede crear, editar ni eliminar clientes
  (RF-05).
- Los roles `freelance_delivery` y `customer` no tienen acceso a ningún endpoint de
  clientes: reciben `403`.

### RF-04 — Edición de clientes (`PUT /customers/:id`)

- Endpoint **protegido**: requiere `Authorization: Bearer <token>` con rol `admin` o
  `seller`.
- Es una **actualización completa**: el cuerpo requiere los mismos campos que la creación
  (`fullName`, `latitude`, `longitude`, `direction`, `isRegistered` y `email`).
  para que el cliente no pueda quedar con datos a medias.
- Responde `200` con los datos públicos actualizados del cliente.
- Si el `id` no corresponde a ningún cliente, responde `404` con
  `{ "message": "Customer not found" }`.
- Si el nuevo `email` ya pertenece a **otro** cliente, responde `409` con
  `{ "message": "Customer already exists" }`.
- Si `:id` no es un entero positivo, responde `422` con
  `{ "errors": { "id": "Invalid customer id" } }`.
- Un usuario con rol `delivery` recibe `403`; sin token, `401`.

### RF-05 — Eliminación de clientes (`DELETE /customers/:id`)

- Endpoint **protegido**: requiere `Authorization: Bearer <token>` con rol `admin` o
  `seller`.
- Elimina de forma permanente al cliente indicado.
- Responde `204` **sin cuerpo** cuando la eliminación es exitosa.
- Si el `id` no corresponde a ningún cliente, responde `404` con
  `{ "message": "Customer not found" }`.
- Si `:id` no es un entero positivo, responde `422` con
  `{ "errors": { "id": "Invalid customer id" } }`.
- Un usuario con rol `delivery` recibe `403`; sin token, `401`.
- La eliminación **no** borra ni modifica usuarios del sistema: los clientes viven en una
  tabla propia (RF-01).

### RF-06 — Autorización por rol

- Se reutilizan los middlewares existentes `authenticate` (HU-01) y
  `authorize(...roles)` (HU-02), apoyados en `req.user.role` del JWT.

  | Endpoint                | `admin` | `seller` | `delivery` | `freelance_delivery` | `customer` |
  | ----------------------- | ------- | -------- | ---------- | -------------------- | ---------- |
  | `POST /customers`       | ✅      | ✅       | ❌ `403`   | ❌ `403`             | ❌ `403`   |
  | `GET /customers`        | ✅      | ✅       | ✅         | ❌ `403`             | ❌ `403`   |
  | `GET /customers/:id`    | ✅      | ✅       | ✅         | ❌ `403`             | ❌ `403`   |
  | `PUT /customers/:id`    | ✅      | ✅       | ❌ `403`   | ❌ `403`             | ❌ `403`   |
  | `DELETE /customers/:id` | ✅      | ✅       | ❌ `403`   | ❌ `403`             | ❌ `403`   |

- Los roles permitidos se expresan con `authorize("admin", "seller")` para escritura y
  `authorize("admin", "seller", "delivery")` para lectura; no se duplican listas de roles en
  los handlers.
- Un usuario bloqueado no puede operar clientes: `authenticate` lo rechaza antes con `403`
  (HU-05).

### RF-07 — Validación de campos

- Se valida con `yup` (mismo enfoque que HU-01/HU-02/HU-03), reutilizando
  `formatValidationErrors`, `missingFields` y `requiredFieldsMessage` mediante el
  middleware `validateRequest` (`src/auth/request-validator.js`).
- Faltan campos obligatorios → `400` con `{ "message": "<campos> are required" }`.
- Campos inválidos → `422` con la estructura de errores y los mensajes **en español**, igual
  que HU-02/HU-03:

  | Campo       | Regla                        | Mensaje              |
  | ----------- | ---------------------------- | -------------------- |
  | `fullName`  | String no vacío.             | `Nombre inválido`    |
  | `latitude`  | Número entre `-90` y `90`.   | `Latitud inválida`   |
  | `longitude` | Número entre `-180` y `180`. | `Longitud inválida`  |
  | `direction` | String no vacío.             | `Dirección inválida` |
  | `email`     | Email bien formado.          | `Email inválido`     |

- Los esquemas viven en `src/customers/validators.js` (`createCustomerSchema`, reutilizado
  por la edición) para no duplicar reglas.
- La validación del parámetro `:id` se hace con un helper reutilizable (p. ej.
  `parseCustomerId`) que devuelve `null` para valores no enteros o menores a `1`; puede
  reutilizarse el patrón de `parseUserId` de `src/users/validators.js`.

## Requerimientos no funcionales

- **RNF-01** — Cada endpoint debe documentarse con un bloque `@openapi` en el router del
  módulo para que sea visible en `/docs` (Swagger UI), incluyendo el esquema `Customer` y
  las respuestas `401`, `403`, `404`, `409` y `422`.
- **RNF-02** — Desarrollo guiado por pruebas (TDD): primero los tests Jest que fallan
  (`src/customers/customers.test.js`), luego la implementación.
- **RNF-03** — Cobertura de pruebas > 90%, con pruebas unitarias (modelo mockeado) y de
  integración contra Postgres real (`src/customers/customers.integration.test.js`).
- **RNF-04** — Ningún archivo debe superar las 300 líneas; si `src/customers/index.js` se
  acerca al límite, extraer los handlers en módulos más pequeños (p. ej.
  `src/customers/list.js` y `src/customers/remove.js`, como en `src/users/`).
- **RNF-05** — Formatear cada archivo modificado con Prettier antes de finalizar.
- **RNF-06** — El acceso a datos se hace con Sequelize 6 sobre Postgres; nunca con consultas
  crudas de `pg`.
- **RNF-07** — Seguridad: el email duplicado se detecta con la restricción única de la base
  de datos (`UniqueConstraintError`) para evitar condiciones de carrera; la API nunca
  devuelve columnas de auditoría.
- **RNF-08** — El listado de clientes no expone datos de usuarios (contraseñas, roles ni
  `isBlocked`): clientes y usuarios son entidades distintas.
- **RNF-09** — La precisión de `latitude`/`longitude` se conserva al serializar (números con
  hasta 7 decimales), sin redondear ni convertir a string.

## Contrato de la API

### `POST /customers`

Header: `Authorization: Bearer <jwt>` (rol `admin` o `seller`).

Petición:

```json
{
  "fullName": "Juan Pérez",
  "latitude": -17.7833,
  "longitude": -63.1821,
  "direction": "Av. Monseñor Rivero 123",
  "email": "juan@example.com"
}
```

Respuesta `201`:

```json
{
  "id": 1,
  "fullName": "Juan Pérez",
  "latitude": -17.7833,
  "longitude": -63.1821,
  "direction": "Av. Monseñor Rivero 123",
  "email": "juan@example.com"
}
```

Respuesta `400` (faltan campos):

```json
{ "message": "fullName, latitude, longitude, direction and email are required" }
```

Respuesta `401` (token ausente, inválido o expirado):

```json
{ "message": "Unauthorized" }
```

Respuesta `403` (rol sin permiso o usuario bloqueado):

```json
{ "message": "Forbidden" }
```

Respuesta `409` (email ya registrado):

```json
{ "message": "Customer already exists" }
```

Respuesta `422` (campos inválidos):

```json
{ "errors": { "latitude": "Latitud inválida" } }
```

### `GET /customers`

Header: `Authorization: Bearer <jwt>` (rol `admin`, `seller` o `delivery`).

Respuesta `200`:

```json
[
  {
    "id": 1,
    "fullName": "Juan Pérez",
    "latitude": -17.7833,
    "longitude": -63.1821,
    "direction": "Av. Monseñor Rivero 123",
    "email": "juan@example.com"
  }
]
```

Respuesta `401` (token ausente, inválido o expirado):

```json
{ "message": "Unauthorized" }
```

Respuesta `403` (rol sin permiso):

```json
{ "message": "Forbidden" }
```

### `GET /customers/:id`

Header: `Authorization: Bearer <jwt>` (rol `admin`, `seller` o `delivery`).

Respuesta `200`:

```json
{
  "id": 1,
  "fullName": "Juan Pérez",
  "latitude": -17.7833,
  "longitude": -63.1821,
  "direction": "Av. Monseñor Rivero 123",
  "email": "juan@example.com"
}
```

Respuesta `404` (el cliente no existe):

```json
{ "message": "Customer not found" }
```

Respuesta `422` (id inválido):

```json
{ "errors": { "id": "Invalid customer id" } }
```

### `PUT /customers/:id`

Header: `Authorization: Bearer <jwt>` (rol `admin` o `seller`).

Petición:

```json
{
  "fullName": "Juan Pérez Gómez",
  "latitude": -17.79,
  "longitude": -63.19,
  "direction": "Av. Monseñor Rivero 456",
  "email": "juan@example.com"
}
```

Respuesta `200`:

```json
{
  "id": 1,
  "fullName": "Juan Pérez Gómez",
  "latitude": -17.79,
  "longitude": -63.19,
  "direction": "Av. Monseñor Rivero 456",
  "email": "juan@example.com"
}
```

Respuesta `404` (el cliente no existe):

```json
{ "message": "Customer not found" }
```

Respuesta `409` (el email pertenece a otro cliente):

```json
{ "message": "Customer already exists" }
```

### `DELETE /customers/:id`

Header: `Authorization: Bearer <jwt>` (rol `admin` o `seller`).

Respuesta `204`: sin cuerpo.

Respuesta `404` (el cliente no existe):

```json
{ "message": "Customer not found" }
```

Respuesta `422` (id inválido):

```json
{ "errors": { "id": "Invalid customer id" } }
```

## Criterios de aceptación

- [ ] Existe la tabla `customers` con `fullName`, `latitude`, `longitude`, `direction` y `email` (todos no nulos) y `email` único.
- [ ] `POST /customers` con rol `admin` o `seller` crea el cliente y responde `201` con sus datos.
- [ ] `POST /customers` con rol `delivery`, `freelance_delivery` o `customer` responde `403`.
- [ ] `POST /customers` sin token responde `401`.
- [ ] `POST /customers` con un email ya registrado responde `409` con `{ "message": "Customer already exists" }`.
- [ ] `POST /customers` con campos faltantes responde `400` y con campos inválidos `422`.
- [ ] `GET /customers` responde `200` con la lista ordenada por `id` ascendente y `[]` cuando no hay clientes.
- [ ] `GET /customers` y `GET /customers/:id` funcionan con rol `admin`, `seller` y `delivery`.
- [ ] `GET /customers` con rol `freelance_delivery` o `customer` responde `403`.
- [ ] `GET /customers/:id` con un id inexistente responde `404` y con un id no numérico `422`.
- [ ] `PUT /customers/:id` actualiza los cinco campos y responde `200` con los datos actualizados.
- [ ] `PUT /customers/:id` con rol `delivery` responde `403`.
- [ ] `PUT /customers/:id` con un email que pertenece a otro cliente responde `409`.
- [ ] `PUT /customers/:id` con un id inexistente responde `404`.
- [ ] `DELETE /customers/:id` elimina el cliente y responde `204` sin cuerpo.
- [ ] `DELETE /customers/:id` con rol `delivery` responde `403`.
- [ ] `DELETE /customers/:id` con un id inexistente responde `404`.
- [ ] Un usuario bloqueado recibe `403` con `{ "message": "User is blocked" }` en todos los endpoints de clientes.
- [ ] Las respuestas nunca incluyen `createdAt`, `updatedAt` ni datos de usuarios.
- [ ] `latitude` y `longitude` se devuelven como números con su precisión original.
- [ ] Los cinco endpoints aparecen documentados en `/docs` y en `README.md`.
- [ ] `npm test` pasa con cobertura > 90%.

## Fuera de alcance

- Pedidos, ventas y asignación de clientes a repartidores.
- Historial de compras o saldo del cliente.
- Geocodificación inversa: la `direction` se recibe tal cual, no se calcula desde las coordenadas.
- Vínculo entre un cliente y un usuario del sistema (`users`): el cliente no inicia sesión.
- Borrado lógico / papelera de clientes: la eliminación es física.
- Paginación, filtros y búsqueda en `GET /customers` (se puede agregar en otra historia).
- Importación masiva de clientes (CSV/Excel).
- Validación de que las coordenadas caigan dentro de un país o ciudad concreta.
