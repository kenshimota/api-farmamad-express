# HU-09 — Email de bienvenida al crear o registrar un usuario

## Historia de usuario

**Como** usuario recién creado o registrado en Super King
**Quiero** recibir un correo de bienvenida en la dirección con la que fui registrado
**Para** confirmar que mi cuenta existe y saber desde qué dirección puedo ingresar a la web.

Además, **como** administrador de Super King
**Quiero** que el correo de bienvenida se envíe automáticamente al crear un usuario
**Para** no tener que avisarle a mano a cada persona que ya tiene acceso al sistema.

Además, **como** desarrollador de la API
**Quiero** que el nombre del producto y la dirección de la web sean configurables por
variables de entorno
**Para** poder cambiar el dominio (hoy `https://dashboard.asic-guanipa.online/`) sin tocar el
código.

## Alcance

Esta historia cubre **únicamente** el envío del correo de bienvenida cuando se crea un usuario:

- El **alta de usuario por el administrador** (`POST /users`), que debe enviar el correo de
  bienvenida.
- El **registro del administrador inicial** (`POST /auth/register-admin`), que debe enviar el
  mismo correo de bienvenida.
- El **contenido del correo**: nombre del producto (`Super King`), link de ingreso
  (`APP_URL`) y mensaje de bienvenida en español.
- La **configuración por variable de entorno** del nombre del producto y del link de ingreso,
  con `Super King` y `https://dashboard.asic-guanipa.online/` como valores por defecto.
- El **renombrado del producto**: donde el correo (y la documentación del proyecto) decía
  `Bread King`, ahora dice `Super King`.

No incluye el registro público de clientes, la confirmación de email, el email de recuperación
de contraseña (HU-03) ni la baja del correo cuando el envío falla (ver _Fuera de alcance_).

## Requerimientos funcionales

### RF-01 — Envío del correo de bienvenida

- Al crear un usuario con `POST /users` (HU-02), después de persistirlo, la API envía un correo
  de bienvenida **a la dirección `email` del usuario creado**.
- Al registrar el administrador inicial con `POST /auth/register-admin` (HU-02), la API envía
  el **mismo** correo de bienvenida al email del administrador creado.
- El envío es **automático**: el cliente no envía ningún campo extra ni elige la plantilla.
- El correo se envía con **Nodemailer** (misma dependencia y mismo transporte Gmail de HU-03,
  `GMAIL_USERNAME` / `GMAIL_TOKEN`), encapsulado en el mailer existente
  (`src/auth/mailer.js`) mediante una función del tipo `sendWelcomeEmail(email, name)`.
- El asunto y el cuerpo del correo son **en español** e incluyen:
  - El nombre del producto (`Super King`).
  - Un saludo de bienvenida, usando el `name` del usuario cuando exista y un saludo genérico
    cuando no.
  - El **link de ingreso** a la web (`APP_URL`), visible como URL completa en el cuerpo.
  - La firma del equipo del producto.
- El correo es **texto plano** (`text`), igual que el correo de recuperación de HU-03; no se
  agrega HTML en esta historia.
- El remitente (`from`) sigue siendo `GMAIL_USERNAME`, sin agregar `MAIL_FROM`.

### RF-02 — El correo no bloquea la creación del usuario

- Si el correo de bienvenida **falla**, el usuario **igual queda creado** y la API responde
  `201` con sus datos públicos: la bienvenida es un efecto secundario, no un requisito del alta.
- El fallo se registra con `logger.error(...)` (HU-04) incluyendo el email del destinatario y
  el error real, para poder reintentar el aviso manualmente.
- El correo se envía **después** de que la transacción de creación haya confirmado, para no
  enviar una bienvenida de un usuario que terminó en `409` (`UniqueConstraintError`) o que se
  revirtió.
- Un `409` por `username` o `email` duplicado **no** envía ningún correo.

### RF-03 — Nombre del producto configurable

- El nombre del producto se lee de la variable de entorno `APP_NAME`.
- Si `APP_NAME` no está definida o está vacía, el valor por defecto es **`Super King`**.
- El nombre se usa en el asunto, en el cuerpo del correo y en la firma.
- El nombre **no** se escribe a mano en el código del mailer: se resuelve desde un único módulo
  de configuración del producto (p. ej. `src/config/product.js`) que expone el nombre y el link
  ya resueltos, para no duplicar el valor por defecto.
- Se reemplaza el literal `Bread King` por el nombre configurado en el correo de recuperación de
  HU-03 (`sendRecoveryCode`), de modo que ambos correos usen el mismo nombre.

### RF-04 — Link de la web configurable

- El link de ingreso se lee de la variable de entorno `APP_URL`.
- Si `APP_URL` no está definida o está vacía, el valor por defecto es
  **`https://dashboard.asic-guanipa.online/`** (con la barra final, tal como se entrega).
- El link se incluye en el cuerpo del correo como URL completa y utilizable; no se le agrega ni
  se le quita la barra final al valor configurado.
- La variable se documenta en `.env.example` y en `README.md`.
- El cambio de dominio futuro se hace **solo** por variable de entorno: ningún módulo debe
  tener el dominio escrito como literal.

### RF-05 — Idempotencia y alcance del envío

- Se envía **exactamente un** correo por usuario creado: ni en el alta del administrador
  inicial ni en `POST /users` se envía el correo dos veces.
- El correo de bienvenida **no** se envía en ningún otro flujo: `POST /auth/login`,
  `POST /auth/forgot-password`, `POST /auth/verify-reset-code` y `POST /auth/reset-password`
  mantienen su comportamiento actual (HU-01/HU-03).
- Los usuarios creados antes de esta historia no reciben correo retroactivo.

### RF-06 — Renombrado del producto

- Donde el proyecto decía `Bread King` ahora dice `Super King`: correos, documentación
  (`README.md`), descripción de Swagger (`title` y `description` de `src/config/swagger.js`) y
  comentarios del código.
- El renombrado es **solo de marca**: no cambia rutas, nombres de tablas, nombres de variables
  de entorno existentes, roles ni contratos de la API.
- Los ejemplos de correo de la documentación (`admin@breadking.com`) se actualizan al dominio
  de marca vigente para no confundir a quien consume la API.

## Requerimientos no funcionales

- **RNF-01** — Los endpoints afectados (`POST /users` y `POST /auth/register-admin`) mantienen
  sus bloques `@openapi` en Swagger, documentando que el alta dispara un correo de bienvenida,
  sin agregar nuevas respuestas al contrato (el envío no cambia el código HTTP).
- **RNF-02** — Desarrollo guiado por pruebas (TDD): primero los tests Jest que fallan
  (`src/auth/mailer.test.js`, `src/users/users.test.js`, `src/auth/bootstrap.test.js` y
  `src/config/product.test.js`), luego la implementación.
- **RNF-03** — Cobertura de pruebas > 90%. En las pruebas el mailer se inyecta o se mockea
  (`setTransport`) para no enviar correos reales ni depender de SMTP.
- **RNF-04** — Ningún archivo debe superar las 300 líneas; el mailer ya está separado del router
  y la configuración del producto vive en su propio módulo.
- **RNF-05** — Formatear cada archivo modificado con Prettier antes de finalizar.
- **RNF-06** — El acceso a datos se hace con Sequelize 6 sobre Postgres; nunca con consultas
  crudas de `pg`. No se agregan dependencias externas: se reutiliza `nodemailer`.
- **RNF-07** — El envío del correo **no** puede hacer fallar el alta: cualquier error del
  transporte se captura, se registra con `logger.error(...)` y la respuesta al cliente sigue
  siendo `201`.
- **RNF-08** — Seguridad: los logs no incluyen tokens ni credenciales; el correo no incluye la
  contraseña del usuario (que además solo existe como hash) ni ningún dato sensible.
- **RNF-09** — El nombre del producto y el link se resuelven una sola vez por envío desde el
  módulo de configuración, de modo que un cambio de variable de entorno se refleje sin reiniciar
  la lógica del mailer.

## Contrato de la API

El correo de bienvenida **no modifica** el contrato HTTP: las respuestas de `POST /users` y
`POST /auth/register-admin` siguen siendo las mismas de HU-02.

### `POST /users`

Header: `Authorization: Bearer <jwt>` (rol `admin`).

Petición:

```json
{
  "username": "maria",
  "email": "maria@example.com",
  "password": "secreto123",
  "name": "María",
  "role": "seller"
}
```

Respuesta `201` (igual que antes; además se envía el correo de bienvenida):

```json
{
  "id": 2,
  "username": "maria",
  "email": "maria@example.com",
  "name": "María",
  "role": "seller",
  "isBlocked": false
}
```

Respuesta `409` (username o email duplicado; **no** se envía correo):

```json
{ "message": "User already exists" }
```

### `POST /auth/register-admin`

Sin autenticación.

Petición:

```json
{
  "username": "admin",
  "email": "admin@example.com",
  "password": "secreto123",
  "name": "Administrador"
}
```

Respuesta `201` (igual que antes; además se envía el correo de bienvenida):

```json
{
  "id": 1,
  "username": "admin",
  "email": "admin@example.com",
  "name": "Administrador",
  "role": "admin"
}
```

### Correo de bienvenida (ejemplo con los valores por defecto)

Asunto:

```text
¡Bienvenido a Super King!
```

Cuerpo (`text/plain`):

```text
Hola María,

¡Te damos la bienvenida a Super King!

Ya puedes ingresar a la web desde:
https://dashboard.asic-guanipa.online/

Si no creaste esta cuenta, ignora este correo.

Equipo Super King
```

Con `APP_NAME=Super King` y `APP_URL=https://dashboard.asic-guanipa.online/` (valores por
defecto) el correo se ve exactamente así; con otras variables cambian el nombre y el link.

### Ejemplo de log cuando el correo no se puede enviar

```text
2026-09-17T10:15:32.104Z ERROR Could not send the welcome email email=maria@example.com :: connection refused
```

El usuario queda creado y la respuesta al cliente sigue siendo `201`.

## Criterios de aceptación

- [ ] Al crear un usuario con `POST /users` se envía un correo de bienvenida al email del usuario creado.
- [ ] Al registrar el administrador inicial con `POST /auth/register-admin` se envía el mismo correo de bienvenida.
- [ ] El correo incluye el nombre del producto (`Super King`), un saludo de bienvenida y el link `https://dashboard.asic-guanipa.online/`.
- [ ] El correo se envía con Nodemailer y el mismo transporte Gmail de HU-03 (`GMAIL_USERNAME` / `GMAIL_TOKEN`).
- [ ] El correo es de texto plano y en español; no incluye HTML ni la contraseña del usuario.
- [ ] Con `APP_NAME` sin definir el nombre del producto es `Super King`.
- [ ] Con `APP_URL` sin definir el link de ingreso es `https://dashboard.asic-guanipa.online/`.
- [ ] Con `APP_NAME` y `APP_URL` definidas, el correo usa esos valores y ningún módulo tiene el dominio escrito a mano.
- [ ] Si el envío del correo falla, el usuario igual queda creado, la respuesta es `201` y el fallo se registra con `logger.error(...)`.
- [ ] Un `409` por `username` o `email` duplicado no envía ningún correo.
- [ ] Se envía exactamente un correo por usuario creado (ni cero ni dos).
- [ ] `POST /auth/login`, `POST /auth/forgot-password`, `POST /auth/verify-reset-code` y `POST /auth/reset-password` no envían correos de bienvenida.
- [ ] El correo de recuperación de contraseña (HU-03) también usa el nombre `Super King`.
- [ ] La documentación (`README.md`, Swagger y comentarios) ya no dice `Bread King` sino `Super King`.
- [ ] `APP_NAME` y `APP_URL` están documentadas en `.env.example` y en `README.md`.
- [ ] `npm test` pasa con cobertura > 90%.

## Fuera de alcance

- Registro público de clientes (`POST /auth/register`) y correo de bienvenida a clientes.
- Confirmación o verificación de email (doble opt-in) y enlaces con token de activación.
- Reintentos automáticos, cola/worker o reproceso de correos fallidos: el envío es síncrono
  dentro de la petición, igual que HU-03.
- Plantillas HTML, imágenes, logotipos o diseño del correo.
- Preferencias de notificación del usuario y baja (unsubscribe) de correos.
- Correo de bienvenida a los usuarios ya existentes antes de esta historia.
- Traducción del correo a otros idiomas.
- Cambio de dominio del remitente, DKIM/SPF o proveedor de correo distinto de Gmail.
