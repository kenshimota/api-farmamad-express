# HU-05 — Administración de usuarios: listado, bloqueo y eliminación

## Historia de usuario

**Como** administrador de Bread King
**Quiero** listar los usuarios registrados y poder bloquear o eliminar a cualquiera de ellos
**Para** mantener el control de quién puede operar el sistema y revocar el acceso de quien ya no debe usarlo.

Además, **como** usuario bloqueado
**Quiero** recibir un mensaje claro cuando intento iniciar sesión
**Para** entender que mi cuenta está suspendida y no que mis credenciales son incorrectas.

## Alcance

Esta historia cubre **únicamente** la administración de usuarios ya existentes:

- El **listado de usuarios** (`GET /users`), exclusivo del administrador.
- El **bloqueo y desbloqueo** de un usuario (`PATCH /users/:id/status`), exclusivo del administrador.
- La **eliminación** de un usuario (`DELETE /users/:id`), exclusiva del administrador.
- El **rechazo del inicio de sesión** (`POST /auth/login`) para usuarios bloqueados, con un
  mensaje que indique que la cuenta está bloqueada.

No incluye edición de datos del usuario (`PUT/PATCH /users/:id`), cambio de rol, registro
público de clientes ni recuperación de contraseña (ver _Fuera de alcance_).

## Requerimientos funcionales

### RF-01 — Estado de bloqueo en el modelo de usuario

- La tabla `users` incorpora la columna booleana **`isBlocked`** (`BOOLEAN`, `allowNull: false`,
  `defaultValue: false`), expuesta en el modelo Sequelize `User` como `isBlocked`.
- Un usuario con `isBlocked: true` está **bloqueado**: no puede iniciar sesión (RF-05) ni
  obtener un nuevo JWT por ningún flujo (`POST /auth/login`, `POST /auth/verify-reset-code`).
- El campo `isBlocked` se expone en las representaciones públicas del usuario (listado y
  detalle) para que el administrador vea el estado actual.
- Al crear un usuario (`POST /users`, HU-02) el valor por defecto es `false`; no se puede
  crear un usuario bloqueado desde el registro.
- Un usuario bloqueado **no se elimina** ni se modifica su contraseña: solo se impide el acceso.

### RF-02 — Listado de usuarios (`GET /users`)

- Endpoint **protegido**: requiere `Authorization: Bearer <token>` con rol `admin`.
- Devuelve la colección de usuarios registrados con los datos públicos de cada uno
  (`id`, `username`, `email`, `name`, `role`, `isBlocked`), **sin** `password` ni `roleId`.
- Responde `200` con un arreglo JSON:

  ```json
  [
    {
      "id": 1,
      "username": "admin",
      "email": "admin@breadking.com",
      "name": "Administrador",
      "role": "admin",
      "isBlocked": false
    },
    {
      "id": 2,
      "username": "maria",
      "email": "maria@breadking.com",
      "name": "María",
      "role": "seller",
      "isBlocked": true
    }
  ]
  ```

- El orden es estable y predecible: por `id` ascendente.
- Si no hay usuarios, responde `200` con `[]` (nunca `404`).
- Un usuario autenticado sin rol `admin` recibe `403` con `{ "message": "Forbidden" }`.
- Sin token, token inválido o expirado responde `401` con `{ "message": "Unauthorized" }`.

### RF-03 — Bloqueo y desbloqueo de usuarios (`PATCH /users/:id/status`)

- Endpoint **protegido**: requiere `Authorization: Bearer <token>` con rol `admin`.
- Cuerpo requerido: `isBlocked` (`boolean`).
- `PATCH /users/:id/status` con `{ "isBlocked": true }` bloquea al usuario; con
  `{ "isBlocked": false }` lo desbloquea.
- Responde `200` con los datos públicos actualizados del usuario (incluido `isBlocked`).
- Si el `id` no corresponde a ningún usuario, responde `404` con
  `{ "message": "User not found" }`.
- Si falta `isBlocked`, responde `400` con `{ "message": "isBlocked is required" }`.
- Si `isBlocked` no es booleano, responde `422` con
  `{ "errors": { "isBlocked": "isBlocked must be a boolean" } }`.
- Si `:id` no es un entero positivo, responde `422` con
  `{ "errors": { "id": "Invalid user id" } }`.
- Un administrador **no puede bloquearse a sí mismo**: responde `409` con
  `{ "message": "You cannot block your own account" }`. Así se evita que el sistema quede
  sin ningún administrador activo.
- Un administrador **no puede bloquear al último administrador activo** distinto de él:
  responde `409` con `{ "message": "Cannot block the last administrator" }`.
- Un usuario autenticado sin rol `admin` recibe `403`; sin token, `401`.

### RF-04 — Eliminación de usuarios (`DELETE /users/:id`)

- Endpoint **protegido**: requiere `Authorization: Bearer <token>` con rol `admin`.
- Elimina de forma permanente al usuario indicado.
- Responde `204` **sin cuerpo** cuando la eliminación es exitosa.
- Si el `id` no corresponde a ningún usuario, responde `404` con
  `{ "message": "User not found" }`.
- Si `:id` no es un entero positivo, responde `422` con
  `{ "errors": { "id": "Invalid user id" } }`.
- Un administrador **no puede eliminarse a sí mismo**: responde `409` con
  `{ "message": "You cannot delete your own account" }`.
- Un administrador **no puede eliminar al último administrador activo**: responde `409` con
  `{ "message": "Cannot delete the last administrator" }`.
- Al eliminar un usuario se eliminan también sus códigos de recuperación de contraseña
  pendientes (`password_reset_codes`), gracias al `onDelete: CASCADE` ya definido en HU-03.
- Un usuario autenticado sin rol `admin` recibe `403`; sin token, `401`.

### RF-05 — Un usuario bloqueado no puede iniciar sesión

- `POST /auth/login` (HU-01) debe comprobar el estado de bloqueo **después** de validar las
  credenciales y **antes** de emitir el JWT.
- Si el usuario está bloqueado, responde `403` con:

  ```json
  { "message": "User is blocked" }
  ```

- El mensaje debe ser **explícito** sobre el bloqueo: no puede confundirse con el `401`
  genérico de credenciales inválidas (`Invalid credentials`), porque el usuario necesita saber
  que su cuenta está suspendida y no que se equivocó al escribir la contraseña.
- La comprobación de bloqueo se hace **después** de verificar la contraseña, para no revelar
  el estado de bloqueo de una cuenta a quien no conoce sus credenciales.
- El mismo criterio aplica a `POST /auth/verify-reset-code` (HU-03): un usuario bloqueado no
  puede iniciar sesión con un código de recuperación válido; responde `403` con
  `{ "message": "User is blocked" }` y el código **no** se consume.
- Un usuario bloqueado con un JWT ya emitido antes del bloqueo sigue siendo rechazado en los
  endpoints protegidos: el middleware de autenticación responde `403` con
  `{ "message": "User is blocked" }` (ver RF-06).

### RF-06 — El bloqueo invalida las sesiones activas

- El middleware `authenticate` (HU-01) debe comprobar que el usuario del token sigue existiendo
  y no está bloqueado; si está bloqueado, responde `403` con `{ "message": "User is blocked" }`.
- Si el usuario del token ya no existe (fue eliminado), responde `401` con
  `{ "message": "Unauthorized" }`.
- Gracias a esta comprobación, bloquear o eliminar a un usuario revoca de inmediato el acceso
  de los JWT que ya tenía emitidos, sin necesidad de una lista negra de tokens.
- La comprobación se hace contra la base de datos con Sequelize (`User.findByPk`), nunca con
  consultas crudas de `pg`.

### RF-07 — Autorización: solo el administrador

- Los tres endpoints nuevos (`GET /users`, `PATCH /users/:id/status`, `DELETE /users/:id`)
  usan el middleware existente `authorize("admin")` (HU-02), apoyado en `req.user.role`.
- Ningún otro rol (`seller`, `delivery`, `freelance_delivery`, `customer`) puede listar,
  bloquear o eliminar usuarios: todos reciben `403` con `{ "message": "Forbidden" }`.
- Tampoco un usuario bloqueado puede administrar usuarios, porque `authenticate` lo rechaza
  antes con `403` (RF-06).

### RF-08 — Validación de campos

- Se valida con `yup` (mismo enfoque que HU-01/HU-02/HU-03), reutilizando
  `formatValidationErrors`, `missingFields` y `requiredFieldsMessage`.
- El esquema del cuerpo de `PATCH /users/:id/status` vive en `src/users/validators.js`
  junto a `createUserSchema`, para no duplicar reglas.
- La validación del parámetro `:id` se hace con un helper reutilizable (p. ej.
  `parseUserId`) que devuelve `null` para valores no enteros o menores a `1`.
- Faltan campos obligatorios → `400` con `{ "message": "<campos> are required" }`.
- Campos inválidos → `422` con la estructura de errores en español, igual que HU-02.

## Requerimientos no funcionales

- **RNF-01** — Cada endpoint nuevo o modificado debe documentarse con un bloque `@openapi`
  en el router del módulo (`src/users/index.js` y `src/auth/index.js`) para que sea visible en
  `/docs` (Swagger UI), incluyendo el campo `isBlocked` en el esquema `User` y las nuevas
  respuestas `403`, `404` y `409`.
- **RNF-02** — Desarrollo guiado por pruebas (TDD): primero los tests Jest que fallan
  (`src/users/users.test.js` y `src/auth/auth.test.js`), luego la implementación.
- **RNF-03** — Cobertura de pruebas > 90%, con pruebas unitarias (modelos mockeados) y de
  integración contra Postgres real (`src/users/users.integration.test.js`,
  `src/auth/auth.integration.test.js`).
- **RNF-04** — Ningún archivo debe superar las 300 líneas; si `src/users/index.js` se acerca
  al límite, extraer el router en módulos más pequeños (p. ej. `src/users/status.js`).
- **RNF-05** — Formatear cada archivo modificado con Prettier antes de finalizar.
- **RNF-06** — El acceso a datos se hace con Sequelize 6 sobre Postgres; nunca con consultas
  crudas de `pg`.
- **RNF-07** — Seguridad: la contraseña nunca aparece en las respuestas; el `403` de bloqueo
  solo se emite después de validar las credenciales (RF-05); el sistema nunca queda sin
  administradores activos (RF-03/RF-04).
- **RNF-08** — El bloqueo y el borrado se ejecutan dentro de una transacción
  (`sequelize.transaction`) para que la comprobación de "último administrador" y la escritura
  no sufran condiciones de carrera.
- **RNF-09** — El listado no debe exponer el hash de la contraseña ni el `roleId`; se reutiliza
  `toPublicUser` de `src/auth/serializers.js` extendido con `isBlocked`.

## Contrato de la API

### `GET /users`

Header: `Authorization: Bearer <jwt>` (rol `admin`).

Respuesta `200`:

```json
[
  {
    "id": 1,
    "username": "admin",
    "email": "admin@breadking.com",
    "name": "Administrador",
    "role": "admin",
    "isBlocked": false
  },
  {
    "id": 2,
    "username": "maria",
    "email": "maria@breadking.com",
    "name": "María",
    "role": "seller",
    "isBlocked": true
  }
]
```

Respuesta `401` (token ausente, inválido o expirado):

```json
{ "message": "Unauthorized" }
```

Respuesta `403` (usuario autenticado sin rol `admin` o usuario bloqueado):

```json
{ "message": "Forbidden" }
```

### `PATCH /users/:id/status`

Header: `Authorization: Bearer <jwt>` (rol `admin`).

Petición:

```json
{ "isBlocked": true }
```

Respuesta `200`:

```json
{
  "id": 2,
  "username": "maria",
  "email": "maria@breadking.com",
  "name": "María",
  "role": "seller",
  "isBlocked": true
}
```

Respuesta `400` (falta `isBlocked`):

```json
{ "message": "isBlocked is required" }
```

Respuesta `404` (el usuario no existe):

```json
{ "message": "User not found" }
```

Respuesta `409` (intento de bloquearse a sí mismo o al último administrador):

```json
{ "message": "You cannot block your own account" }
```

Respuesta `422` (id o `isBlocked` inválidos):

```json
{ "errors": { "isBlocked": "isBlocked must be a boolean" } }
```

### `DELETE /users/:id`

Header: `Authorization: Bearer <jwt>` (rol `admin`).

Respuesta `204`: sin cuerpo.

Respuesta `404` (el usuario no existe):

```json
{ "message": "User not found" }
```

Respuesta `409` (intento de eliminarse a sí mismo o al último administrador):

```json
{ "message": "You cannot delete your own account" }
```

Respuesta `422` (id inválido):

```json
{ "errors": { "id": "Invalid user id" } }
```

### `POST /auth/login` (usuario bloqueado)

Petición:

```json
{ "identifier": "maria@breadking.com", "password": "secreto123" }
```

Respuesta `403` (credenciales correctas pero cuenta bloqueada):

```json
{ "message": "User is blocked" }
```

## Criterios de aceptación

- [ ] La tabla `users` tiene la columna `isBlocked` (booleana, no nula, por defecto `false`).
- [ ] `GET /users` devuelve la lista de usuarios con `isBlocked` y sin `password` ni `roleId`.
- [ ] `GET /users` responde `[]` cuando no hay usuarios y `403` para roles distintos de `admin`.
- [ ] `GET /users` sin token responde `401`.
- [ ] `PATCH /users/:id/status` con `{ "isBlocked": true }` bloquea al usuario y responde `200`.
- [ ] `PATCH /users/:id/status` con `{ "isBlocked": false }` desbloquea al usuario y responde `200`.
- [ ] `PATCH /users/:id/status` con un `id` inexistente responde `404`.
- [ ] `PATCH /users/:id/status` sin `isBlocked` responde `400` y con un valor no booleano `422`.
- [ ] Un administrador no puede bloquearse a sí mismo (`409`) ni bloquear al último administrador activo (`409`).
- [ ] `DELETE /users/:id` elimina al usuario y responde `204` sin cuerpo.
- [ ] `DELETE /users/:id` con un `id` inexistente responde `404`.
- [ ] Un administrador no puede eliminarse a sí mismo (`409`) ni eliminar al último administrador (`409`).
- [ ] Al eliminar un usuario se eliminan sus códigos de recuperación pendientes.
- [ ] Un usuario bloqueado que intenta `POST /auth/login` con credenciales correctas recibe `403` con `{ "message": "User is blocked" }`.
- [ ] Un usuario bloqueado no puede iniciar sesión con un código de recuperación válido (`POST /auth/verify-reset-code` responde `403`).
- [ ] Un usuario bloqueado con un JWT emitido antes del bloqueo recibe `403` en los endpoints protegidos.
- [ ] Un usuario eliminado con un JWT vigente recibe `401` en los endpoints protegidos.
- [ ] Los roles `seller`, `delivery`, `freelance_delivery` y `customer` reciben `403` en los tres endpoints de administración.
- [ ] La contraseña nunca aparece en las respuestas del listado ni del bloqueo.
- [ ] Los tres endpoints y el `403` de bloqueo aparecen documentados en `/docs` y en `README.md`.
- [ ] `npm test` pasa con cobertura > 90%.

## Fuera de alcance

- Edición de los datos del usuario (`PUT/PATCH /users/:id`): nombre, email, username o rol.
- Cambio de rol y asignación de permisos granulares por rol.
- Registro público de clientes (`POST /auth/register`).
- Desbloqueo automático por tiempo (bloqueo temporal con fecha de expiración).
- Lista negra de tokens o revocación selectiva de JWT (el bloqueo se resuelve consultando la
  base de datos en `authenticate`).
- Soft delete / papelera de usuarios: la eliminación es física.
- Auditoría histórica de quién bloqueó o eliminó a quién (más allá de los logs de acceso de HU-04).
- Paginación, filtros y búsqueda en `GET /users` (se puede agregar en otra historia).
