# HU-02 — Roles de usuario, creación de usuarios y bootstrap del administrador

## Historia de usuario

**Como** administrador de Farmamad
**Quiero** que todos los usuarios tengan un rol asignado y poder crear usuarios desde la API
**Para** controlar quién puede operar el sistema y arrancar la operación cuando la base de datos
todavía no tiene ningún usuario.

Además, **como** cliente de la API
**Quiero** consultar si el sistema ya tiene un administrador registrado
**Para** saber si debo mostrar el formulario de registro inicial del administrador.

## Alcance

Esta historia cubre:

- Los **roles** disponibles en el sistema y su asignación a cada usuario.
- El **registro del usuario administrador inicial** (bootstrap), permitido únicamente cuando
  el sistema no tiene administrador.
- La **creación de usuarios por parte del administrador** (`POST /users`).
- El **endpoint de consulta del estado de bootstrap** (`GET /auth/setup-status`).

No incluye edición, desactivación ni listado de usuarios, ni el registro público de clientes
(ver _Fuera de alcance_).

## Requerimientos funcionales

### RF-01 — Roles del sistema

- Todo usuario debe tener **exactamente un rol** (campo obligatorio `role`).
- Los roles válidos son, en minúsculas y sin acentos, los siguientes:

  | Valor del rol       | Descripción                                                  |
  | ------------------- | ------------------------------------------------------------ |
  | `administrador`     | Administra el sistema; es el único que puede crear usuarios. |
  | `vendedora`         | Gestiona ventas y pedidos.                                   |
  | `delivery`          | Repartidor que pertenece a la empresa.                       |
  | `delivery_autonomo` | Repartidor independiente que no pertenece a la empresa.      |
  | `cliente`           | Usuario final que compra los productos.                      |

- Los roles se almacenan en una **tabla `roles`** (modelo Sequelize `Role`), **no** como `ENUM`
  de Postgres ni como lista fija en el código.
- Cada rol tiene como mínimo los campos `id` y `name` en ingles (único, no nulo). El `name` es el valor
  listado en la tabla anterior y es el que viaja en la API.
- La tabla `roles` se puebla mediante un **seeder** con los cinco roles anteriores, para que
  existan en cualquier entorno (desarrollo, pruebas y producción).
- La tabla `users` se relaciona con `roles` mediante una **clave foránea `roleId`**
  (`allowNull: false`), con la asociación Sequelize `User.belongsTo(Role)` y
  `Role.hasMany(User)`.
- La API expone el rol como **nombre** (`role: "administrador"`), nunca como `roleId`.
- Si la petición no envía `role`, el sistema asigna el rol `cliente` por defecto.
- Un rol distinto a los listados produce `422` con el error de validación correspondiente.

### RF-02 — Estado de bootstrap (`GET /auth/setup-status`)

- Endpoint público (no requiere autenticación).
- Indica si el sistema ya tiene **al menos un usuario con rol `administrador`**.
- Responde `200` con la siguiente estructura:

  ```json
  { "hasAdmin": false }
  ```

- `hasAdmin` es `false` cuando no existe ningún administrador y `true` en caso contrario.
- Este endpoint es el que permite a un cliente decidir si debe ofrecer el registro inicial.

### RF-03 — Registro del administrador inicial (`POST /auth/register-admin`)

- Endpoint público (no requiere autenticación).
- Solo se permite cuando el sistema **no tiene ningún administrador**.
- Campos requeridos en el cuerpo: `username`, `email` y `password`.
- Campos opcionales: `name`.
- El rol del usuario creado es siempre `administrador`; el cliente **no** puede elegirlo.
- Si la creación es exitosa responde `201` con los datos públicos del usuario (sin `password`).
- Si ya existe un administrador, responde `409` con `{ "message": "Admin already exists" }`.
- La contraseña se almacena como hash bcrypt (mismo hook del modelo `User`).

### RF-04 — Creación de usuarios por el administrador (`POST /users`)

- Endpoint protegido: requiere `Authorization: Bearer <token>`.
- Solo un usuario autenticado con rol `administrador` puede invocarlo.
- Campos requeridos: `username`, `email`, `password` y `role`.
- Campos opcionales: `name`.
- `role` debe ser el nombre de uno de los roles de RF-01.
- `username` y `email` deben ser únicos; si ya existen, responde `409`.
- Si la creación es exitosa responde `201` con los datos públicos del usuario (sin `password`).
- Un usuario autenticado sin rol `administrador` recibe `403` con
  `{ "message": "Forbidden" }`.
- La contraseña se almacena como hash bcrypt (mismo hook del modelo `User`).

### RF-05 — Autenticación y autorización

- El JWT emitido en `POST /auth/login` (HU-01) debe incluir el `role` del usuario en el payload.
- `GET /auth/me` debe devolver también el `role` del usuario autenticado.
- El middleware de autorización (`authorize("administrador")`) se apoya en `req.user.role`
  y responde `403` cuando el rol no está permitido.
- Si el token falta, es inválido o está expirado, se mantiene el comportamiento de HU-01: `401`.

### RF-06 — Validación de campos

- Se valida con `yup` (mismo enfoque que HU-01).
- Faltan campos obligatorios → `400` con `{ "message": "<campos> are required" }`.
- Campos inválidos (email mal formado, contraseña corta, rol inexistente) → `422` con la
  estructura de errores:

  ```json
  { "errors": { "role": "Invalid role" } }
  ```

- La contraseña debe tener al menos 8 caracteres (misma regla que HU-01).
- La validación de `role` se hace contra los roles existentes en la tabla `roles`, no contra
  una lista duplicada en el validador.

## Requerimientos no funcionales

- **RNF-01** — Cada endpoint debe documentarse con un bloque `@openapi` en el router del módulo
  para que sea visible en `/docs` (Swagger UI), incluyendo los nuevos esquemas `Role` y `User`.
- **RNF-02** — Desarrollo guiado por pruebas (TDD): primero el test Jest que falla
  (`src/users/users.test.js`), luego la implementación.
- **RNF-03** — Cobertura de pruebas > 90%.
- **RNF-04** — Ningún archivo debe superar las 300 líneas; dividir en módulos si es necesario.
- **RNF-05** — Formatear cada archivo modificado con Prettier antes de finalizar.
- **RNF-06** — El acceso a datos se hace con Sequelize 6 sobre Postgres; nunca con consultas
  crudas de `pg`.
- **RNF-07** — La lista de roles vive en un único lugar: la tabla `roles` (poblada por el
  seeder) y su modelo `Role`. El código (validadores, middlewares y Swagger) debe derivar de
  ahí la lista de roles válidos para evitar duplicarla.
- **RNF-08** — El endpoint `POST /auth/register-admin` debe ser seguro frente a concurrencia:
  la comprobación de "ya existe administrador" y la inserción deben ejecutarse dentro de una
  transacción para evitar crear dos administradores simultáneamente.

## Contrato de la API

### `GET /auth/setup-status`

Sin autenticación.

Respuesta `200`:

```json
{ "hasAdmin": false }
```

### `POST /auth/register-admin`

Sin autenticación.

Petición:

```json
{
  "username": "admin",
  "email": "admin@farmamad.com",
  "password": "secreto123",
  "name": "Administrador"
}
```

Respuesta `201`:

```json
{
  "id": 1,
  "username": "admin",
  "email": "admin@farmamad.com",
  "name": "Administrador",
  "role": "administrador"
}
```

Respuesta `409` (ya existe un administrador):

```json
{ "message": "Admin already exists" }
```

Respuesta `422` (campos inválidos):

```json
{ "errors": { "email": "Invalid email" } }
```

### `POST /users`

Header: `Authorization: Bearer <jwt>` (rol `administrador`).

Petición:

```json
{
  "username": "maria",
  "email": "maria@farmamad.com",
  "password": "secreto123",
  "name": "María",
  "role": "vendedora"
}
```

Respuesta `201`:

```json
{
  "id": 2,
  "username": "maria",
  "email": "maria@farmamad.com",
  "name": "María",
  "role": "vendedora"
}
```

Respuesta `401` (token ausente, inválido o expirado):

```json
{ "message": "Unauthorized" }
```

Respuesta `403` (usuario autenticado sin rol administrador):

```json
{ "message": "Forbidden" }
```

Respuesta `409` (username o email duplicado):

```json
{ "message": "User already exists" }
```

Respuesta `422` (rol inválido):

```json
{ "errors": { "role": "Invalid role" } }
```

## Criterios de aceptación

- [ ] Existe la tabla `roles` poblada con los cinco roles de RF-01 en cualquier entorno.
- [ ] La tabla `users` tiene una clave foránea `roleId` hacia `roles`, no nula.
- [ ] `GET /auth/setup-status` responde `hasAdmin: false` cuando no hay administradores.
- [ ] `GET /auth/setup-status` responde `hasAdmin: true` cuando ya existe un administrador.
- [ ] Puedo registrar el administrador inicial con `POST /auth/register-admin` y recibo `201`.
- [ ] Un segundo intento de `POST /auth/register-admin` responde `409`.
- [ ] El administrador puede crear usuarios con cualquier rol válido vía `POST /users`.
- [ ] Un usuario con rol `vendedora`, `delivery`, `delivery_autonomo` o `cliente` recibe `403`
      al llamar `POST /users`.
- [ ] `POST /users` sin token responde `401`.
- [ ] Crear un usuario con `username` o `email` repetido responde `422` con su estructura de errores indicando de que ya ha sido tomado.
- [ ] Crear un usuario con un rol inexistente responde `422`.
- [ ] El JWT y `GET /auth/me` incluyen el `role` del usuario.
- [ ] La contraseña nunca aparece en ninguna respuesta ni se guarda en texto plano.
- [ ] Todos los endpoints aparecen documentados en `/docs`.
- [ ] `npm test` pasa con cobertura > 90%.
- [ ] los errores de validación de campos deberian expresar el mensaje en español.

## Fuera de alcance

- Edición, desactivación, listado y borrado de usuarios (`GET/PUT/PATCH/DELETE /users`).
- CRUD de roles (`GET/POST/PUT/DELETE /roles`): los roles son fijos y se cargan por seeder.
- Registro público de clientes (`POST /auth/register`).
- Recuperación / cambio de contraseña.
- Permisos granulares por rol más allá de "solo administrador crea usuarios".
- Refresh tokens y cierre de sesión.
