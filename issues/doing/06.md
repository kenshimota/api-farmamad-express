# HU-06 — CORS: permitir el consumo de la API desde cualquier origen

## Historia de usuario

**Como** cliente de la API de Bread King (aplicación web, móvil o cualquier frontend
en desarrollo)
**Quiero** poder consumir los endpoints desde cualquier origen sin que el navegador
bloquee mis peticiones
**Para** integrar la API hoy mismo sin depender de que el equipo configure una lista
de dominios permitidos.

Además, **como** desarrollador de la API
**Quiero** que la política de CORS viva en un único lugar y sea configurable por
variable de entorno
**Para** poder pasar de `*` a una lista explícita de orígenes cuando el proyecto lo
necesite, sin tocar el código de los módulos.

## Alcance

Esta historia cubre **únicamente** la capa transversal de CORS de la API:

- La habilitación de CORS para **todos** los orígenes (`*`) en todas las rutas.
- La respuesta correcta a las **peticiones preflight** (`OPTIONS`) que el navegador
  envía antes de una petición con `Authorization` o `Content-Type: application/json`.
- La exposición de la cabecera `X-Request-Id` (HU-04) a los clientes del navegador.
- La configuración del origen permitido mediante una **variable de entorno**, con `*`
  como valor por defecto.

No incluye autenticación basada en cookies, credenciales de navegador
(`Access-Control-Allow-Credentials`) ni una lista blanca de dominios por entorno (ver
_Fuera de alcance_).

## Requerimientos funcionales

### RF-01 — CORS habilitado para todos los orígenes

- La API responde con la cabecera `Access-Control-Allow-Origin` en **todas** las
  respuestas, incluidas las de error (`400`, `401`, `403`, `404`, `409`, `422`, `429`,
  `500`, `502`, `503`).
- Por defecto el valor es `*`, de modo que cualquier origen puede consumir la API.
- El middleware de CORS se registra **antes** que cualquier router en `src/app.js`,
  para que también cubra las respuestas de `notFound` y `errorHandler` (HU-04).
- La habilitación aplica a todos los módulos existentes (`/hello-world`, `/health`,
  `/auth`, `/users`) y a `/docs` (Swagger UI), sin excepciones.

### RF-02 — Peticiones preflight (`OPTIONS`)

- Toda petición `OPTIONS` dirigida a una ruta existente responde `204` (sin cuerpo)
  con las cabeceras CORS correspondientes, sin llegar a los routers de negocio.
- Las cabeceras preflight incluyen como mínimo:
  - `Access-Control-Allow-Origin: *`
  - `Access-Control-Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS`
  - `Access-Control-Allow-Headers: Content-Type,Authorization,X-Request-Id`
  - `Access-Control-Max-Age` (por ejemplo `86400`) para que el navegador cachee el
    preflight y no lo repita en cada petición.
- El preflight funciona igual para rutas protegidas (`Authorization`) y para rutas con
  cuerpo JSON (`Content-Type: application/json`), que son las que disparan el
  preflight en el navegador.
- Una petición `OPTIONS` a una ruta inexistente sigue respondiendo `404` con
  `{ "message": "Not found" }` (HU-04), pero con las cabeceras CORS presentes.

### RF-03 — Cabeceras expuestas al cliente

- La respuesta expone la cabecera `X-Request-Id` (HU-04) mediante
  `Access-Control-Expose-Headers: X-Request-Id`, para que un frontend pueda leerla y
  correlacionar un error con su línea de log.
- No se exponen cabeceras sensibles (`Authorization`, `Set-Cookie`).

### RF-04 — Origen configurable por variable de entorno

- El origen permitido se lee de la variable `CORS_ORIGIN`.
- Si `CORS_ORIGIN` no está definida o está vacía, se usa `*` (comportamiento por
  defecto de esta historia).
- Si `CORS_ORIGIN` contiene varios orígenes separados por comas (p. ej.
  `https://app.breadking.com,https://admin.breadking.com`), cada uno se permite de
  forma explícita y el middleware responde con el origen de la petición cuando
  coincide.
- La variable se documenta en `.env.example` y en `README.md`.
- El valor `*` se mantiene como **decisión temporal y explícita**: el código debe
  dejar claro (comentario en inglés) que se relajará cuando exista la lista de
  dominios definitiva.

### RF-05 — Sin credenciales de navegador

- Como el origen es `*`, la API **no** habilita
  `Access-Control-Allow-Credentials: true`; las peticiones se autentican con el
  header `Authorization: Bearer <jwt>`, no con cookies.
- Si en el futuro se necesita enviar cookies, esta historia deberá revisarse porque
  `Access-Control-Allow-Credentials: true` es incompatible con
  `Access-Control-Allow-Origin: *`.

## Requerimientos no funcionales

- **RNF-01** — La configuración de CORS vive en un único módulo
  (`src/config/cors.js`) y se registra una sola vez en `src/app.js`; ningún router
  define cabeceras CORS por su cuenta.
- **RNF-02** — Desarrollo guiado por pruebas (TDD): primero los tests Jest que fallan
  (`src/config/cors.test.js` y `src/app.test.js`), luego la implementación.
- **RNF-03** — Cobertura de pruebas > 90%, cubriendo respuestas exitosas, respuestas
  de error, preflight y rutas inexistentes.
- **RNF-04** — Ningún archivo debe superar las 300 líneas.
- **RNF-05** — Formatear cada archivo modificado con Prettier antes de finalizar.
- **RNF-06** — Sin dependencias nuevas: se implementa un middleware propio sobre
  Express 5 (o, si el equipo lo prefiere, se evalúa `cors`, pero no se agrega sin
  justificarlo en el MR).
- **RNF-07** — El middleware de CORS no debe romper los endpoints existentes ni
  alterar sus cuerpos de respuesta: solo agrega cabeceras y responde el preflight.
- **RNF-08** — El preflight se resuelve sin consultar la base de datos ni ejecutar
  lógica de negocio, para no penalizar la latencia de cada petición del navegador.
- **RNF-09** — Seguridad: no se expone ninguna cabecera sensible y el `500` sigue
  devolviendo el mensaje genérico de HU-04.

## Contrato de la API

### Respuesta con CORS (cualquier endpoint)

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: *
Access-Control-Expose-Headers: X-Request-Id
Content-Type: application/json
```

### Preflight `OPTIONS /users`

```http
OPTIONS /users HTTP/1.1
Origin: http://localhost:5173
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization,content-type
```

Respuesta `204`:

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS
Access-Control-Allow-Headers: Content-Type,Authorization,X-Request-Id
Access-Control-Max-Age: 86400
```

### Respuesta de error con CORS

```http
HTTP/1.1 401 Unauthorized
Access-Control-Allow-Origin: *
Content-Type: application/json

{ "message": "Unauthorized" }
```

### Ejemplo de consumo desde el navegador

```js
// Any origin can call the API today; CORS_ORIGIN will restrict it later.
const response = await fetch("http://localhost:3001/users", {
  headers: { Authorization: `Bearer ${token}` },
});
const requestId = response.headers.get("X-Request-Id");
```

## Criterios de aceptación

- [ ] Toda respuesta de la API incluye `Access-Control-Allow-Origin: *`.
- [ ] Las respuestas de error (`401`, `403`, `404`, `422`, `500`) también incluyen la
      cabecera CORS.
- [ ] Una petición `OPTIONS` a una ruta existente responde `204` con
      `Access-Control-Allow-Methods` y `Access-Control-Allow-Headers`.
- [ ] Una petición `OPTIONS` a una ruta inexistente responde `404` en JSON y con
      cabeceras CORS.
- [ ] El navegador puede leer la cabecera `X-Request-Id` de la respuesta.
- [ ] Con `CORS_ORIGIN` sin definir el origen permitido es `*`.
- [ ] Con `CORS_ORIGIN` definida con varios orígenes, solo esos orígenes reciben
      `Access-Control-Allow-Origin` con su propio valor.
- [ ] No se envía `Access-Control-Allow-Credentials: true`.
- [ ] Los endpoints existentes (`/hello-world`, `/health`, `/auth/*`, `/users`) siguen
      respondiendo igual: CORS solo agrega cabeceras.
- [ ] La política de CORS está documentada en `README.md` y la variable `CORS_ORIGIN`
      en `.env.example`.
- [ ] `npm test` pasa con cobertura > 90%.

## Fuera de alcance

- `Access-Control-Allow-Credentials: true` y autenticación basada en cookies.
- Lista blanca de orígenes por entorno (dev/staging/producción) gestionada desde el
  panel de despliegue.
- CORS selectivo por ruta o por método (la política es global).
- Protección CSRF (la API es *stateless* y usa `Authorization: Bearer`).
- Rate limiting por origen o por IP.
- Cambios en la lógica de autenticación, roles o bloqueo de usuarios.

  | `CORS_ORIGIN` | Origen(es) permitido(s) separados por comas; por defecto `*` (todos).      |

    cabeceras expuestas).
  - `src/config/cors.test.js` — pruebas Jest del middleware.
- Archivos a modificar:
  - `src/app.js` — registrar el middleware de CORS antes de los routers.
  - `src/app.test.js` — cubrir cabeceras CORS en respuestas exitosas, errores y
    preflight.
  - `README.md` — documentar la política de CORS, el preflight y `CORS_ORIGIN`.
  - `.env.example` — agregar `CORS_ORIGIN`.
